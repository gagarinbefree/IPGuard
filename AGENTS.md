# AGENTS.md — IPGuard

## Цель проекта

Разработай полноценное приложение для Windows 10/11 на C# и .NET 10, которое автоматически контролирует доступ PowerShell (`powershell.exe` и `pwsh.exe`) к интернету в зависимости от географического расположения **внешнего публичного IP-адреса компьютера**, аналогичного адресу, который показывают 2ip.ru и 2ip.com. Если внешний IP достоверно определяется как принадлежащий США (`US`), сетевой доступ PowerShell разрешается; если адрес принадлежит другой стране, не определяется или проверка завершается ошибкой — доступ блокируется. Не путай геолокацию внешнего IP компьютера с геолокацией IP удалённого сервера.

## Обязательные требования

1. Реализуй настольное приложение с иконкой в системном трее и графическим интерфейсом на **Avalonia**, **Avalonia.Markup.Declarative** и **CommunityToolkit.Mvvm**. Windows Service не создавай и не устанавливай. Управляй доступом через штатный Windows Firewall или Windows Filtering Platform (WFP) без собственного драйвера ядра. Сначала проверь фактические возможности выбранного механизма, особенно приоритет разрешающих и блокирующих правил. Не обещай режим, который Windows Firewall не способен обеспечить.
2. Применяй **fail-closed**: блокировка должна действовать по умолчанию до успешной проверки, при загрузке Windows, до запуска GUI, при закрытии, сбое или остановке приложения. Сворачивание и закрытие окна должны скрывать его в трей; выход из приложения — отдельное явное действие с сохранением блокировки. Обеспечь безопасное восстановление политики и корректное удаление только собственных правил при деинсталляции.
3. Определяй публичные IPv4 и IPv6 через несколько независимых HTTPS-источников с таймаутами, TLS-проверкой и обработкой несовпадающих результатов. Используй локальную GeoIP-базу и предусмотренное обновление базы. При неоднозначности блокируй доступ.
4. Отслеживай изменения сетевых интерфейсов, маршрутов, VPN, публичных адресов и периодически перепроверяй состояние. Учитывай split tunneling, прокси и IPv6: IP, показанный HTTPS-сервисом, сам по себе не доказывает, что **весь** трафик PowerShell идёт через тот же выходной адрес. Если это нельзя подтвердить, сохраняй блокировку и явно показывай причину.
5. При потере разрешённого состояния немедленно блокируй новые соединения. Отдельно исследуй и протестируй судьбу уже установленных соединений; не утверждай, что они гарантированно разрываются, если механизм этого не обеспечивает.
6. Поддерживай Windows PowerShell 5.1 и PowerShell 7+, включая разные пути установки. Не ограничивай сетевой доступ остальных приложений. Отдельно документируй, что блокировка исполняемых файлов PowerShell не эквивалентна блокировке дочерних процессов (`curl.exe`, `python.exe`, `git.exe` и т. п.) и не является защитой от администратора системы.
7. Реализуй JSON-конфигурацию с разрешёнными странами (по умолчанию только `US`), интервалами проверки, источниками публичного IP и настройками логирования. Добавь структурированные журналы, GUI и CLI для диагностики приложения: внешний IP, страна, состояние VPN/маршрута, последняя проверка, причина решения и **фактическое** состояние блокировки. GUI должен позволять просматривать состояние, менять настройки и запускать повторную проверку без блокировки UI-потока.
8. Реализуй безопасную установку, запуск, выход, настройку автозапуска приложения при входе пользователя и удаление; используй уникальные идентификаторы собственных правил, обработку конфликтов и принцип минимальных привилегий. Отдельно исследуй права для Firewall/WFP и модель повышения привилегий без Windows Service. Автозапуск GUI сам по себе не обеспечивает блокировку до входа пользователя.

## Архитектура и качество

### Платформа и границы

- Используй C# и .NET 10, строгие настройки компилятора и nullable reference types.
- Для GUI используй Avalonia и декларативную разметку на C# через Avalonia.Markup.Declarative; для MVVM — CommunityToolkit.Mvvm. Не заменяй этот стек WPF, WinForms или другой MVVM-библиотекой.
- Сейчас реализуй и проверяй приложение только для Windows 10/11. Архитектура должна позволять добавлять поддержку других ОС заменой платформенных реализаций.
- Решение называется `IPGuard`. Имена проектов — без префикса `IPGuard.`: `Domain`, `Application`, `Infrastructure`, `Windows`, `Desktop`, `Cli`, `UnitTests`, `IntegrationTests`. Создавай проекты по мере появления нужного кода; проект `Service` не нужен.
- Сообщения коммитов пиши на английском простыми словами, например `Add Windows build` или `Fix tray menu`. CI пока собирает и проверяет только Windows x64; не добавляй сборки для других ОС без соответствующей задачи.
- Применяй Clean Architecture и Dependency Injection соразмерно задаче: доменная политика не должна зависеть от Windows API, сетевого транспорта, Avalonia, MVVM Toolkit или CLI.
- Разделяй доменную политику, получение внешнего IP, GeoIP, мониторинг сети, управление Firewall/WFP, GUI с треем, CLI и инфраструктуру логирования. ViewModel не должна обращаться к Firewall/WFP напрямую; GUI и CLI используют общие сценарии приложения.
- Скрывай зависимости от ОС и сети за тестируемыми интерфейсами. Размещай Windows API и платформенные проверки в Windows-инфраструктуре, не распространяй их по доменной логике.
- Для будущей ОС должно быть достаточно добавить нужные адаптеры и хостинг, сохранив общую политику принятия решений и её тесты. Не создавай заранее проекты, реализации и универсальные платформенные слои для неподдерживаемых ОС.

### Принципы проектирования

- **Одна ответственность:** каждый класс, метод и самостоятельный фрагмент кода решает одну понятную задачу. Разделяй получение данных, принятие решения и применение побочных эффектов.
- **Композиция вместо наследования:** не используй наследование классов в собственном коде. Собирай поведение из небольших компонентов; используй интерфейсы для контрактов и внедрение зависимостей. Не создавай базовые классы для повторного использования кода, в том числе в тестах.
- **DRY:** держи каждое бизнес-правило, знание о конфигурации и значимое поведение в одном месте. Объединяй подтверждённое дублирование; внешне похожие фрагменты с разными причинами изменения не обязаны иметь общую абстракцию.
- **KISS:** выбирай самое простое решение, которое полностью выполняет текущие требования. Предпочитай явный поток управления, понятные имена и небольшие компоненты. Избегай скрытой магии, сложных цепочек и метапрограммирования без доказанной необходимости.
- **YAGNI:** реализуй только требуемое сейчас поведение. Не добавляй функции, точки расширения, настройки, зависимости и обобщения «на будущее». Требуемую переносимость обеспечивай границами уже необходимых компонентов.
- Применяй SOLID в рамках этих правил. Не создавай интерфейс для каждого класса, формальные слои и шаблоны проектирования без конкретной пользы.
- Не используй заглушки вместо критически важной функциональности в итоговом продукте.

### Читаемость, документация и развитие проекта

- Пиши код для людей: ясность важнее краткости и демонстрации возможностей языка. Избегай «умного» кода, неочевидных сокращений и преждевременной оптимизации.
- Пиши все комментарии в коде, включая XML-документацию и комментарии в тестах, на английском языке. `README.md` также веди на английском. Это правило не задаёт язык пользовательского интерфейса.
- Добавляй XML-комментарии `///` ко всем написанным вручную классам, методам и свойствам, включая непубличные. Документируй также конструкторы и члены интерфейсов. Это правило распространяется на тестовый код; автоматически сгенерированные файлы не редактируй.
- В `<summary>` объясняй назначение и контракт. При необходимости добавляй `<param>`, `<returns>`, `<exception>` и `<remarks>` для условий, единиц измерения, побочных эффектов и существенных ограничений. Комментарий должен помогать понять поведение, а не повторять имя элемента.
- Поддерживай комментарии одновременно с изменением поведения. Внутри методов комментируй причины неочевидных решений; очевидные действия должны читаться из кода.
- Делай добавление функциональности и создание форков понятными: используй последовательную структуру и именование, явные контракты и небольшие зависимости. Когда появляется реальный способ расширения, документируй в README, какой компонент добавить или заменить и какими тестами подтвердить поведение.
- Не отключай Windows Firewall целиком, не меняй чужие правила и не блокируй сетевой доступ разработчика в ходе обычных тестов.

## Обязательный процесс TDD

1. Изучи возможности Windows Firewall/WFP, ограничения прав, правила приоритета, обработку существующих соединений и способы проверки фактического исходящего маршрута. Зафиксируй решения и риски.
2. Составь план реализации небольшими этапами с измеримыми критериями приёмки.
3. Для каждого этапа сначала напиши падающие тесты, затем минимальную реализацию, затем проведи рефакторинг.
4. Используй xUnit для unit-тестов и отдельные интеграционные тесты. Покрой смену IP и страны, VPN disconnect/reconnect, DNS/HTTPS/GeoIP failures, конфликт источников, IPv4/IPv6, split tunneling, рестарт и падение приложения, конфликт правил Firewall и fail-closed. Для GUI проверь ViewModel, скрытие окна в трей, явный выход и сохранение блокировки после завершения процесса.
5. Реальные интеграционные тесты, меняющие Firewall, запускай **только** после явного включения специального режима в изолированной Windows VM с правами администратора. Обычный `dotnet test` должен быть безопасным для рабочей машины.
6. После каждого этапа запускай тесты и сборку, сообщай результаты и ограничения. Успешная компиляция не является доказательством работоспособности сетевой блокировки.
