# Техническое исследование IPGuard

Дата проверки источников: 22–24 октября 2026 года.

IPGuard будет настольным приложением с треем на .NET 10, Avalonia, Avalonia.Markup.Declarative и CommunityToolkit.Mvvm. Собственный Windows Service и драйвер ядра исключены. Для прототипа выбран пользовательский API WFP. Пригодность схемы для выпуска зависит от испытаний, перечисленных в [программе проверок VM](vm-validation.md).

Основной риск — различие между наблюдением адреса и обеспечением маршрута: несколько HTTPS-ответов с адресом США не доказывают, что произвольное соединение PowerShell использует тот же внешний выход. При отсутствии достаточного подтверждения решение остаётся блокирующим. Геолокация адреса удалённого сервера в принятии решения не участвует.

## Выбор механизма фильтрации

| Вариант | Возможности и ограничения | Решение |
| --- | --- | --- |
| Обычные правила Windows Firewall | Явный Block перекрывает конфликтующий Allow. Отключённый на время разрешения Block сам не восстанавливается при падении GUI. | Не использовать как основу временного разрешения с fail-closed. |
| Пользовательский API WFP | Есть собственные sublayer, веса фильтров, транзакции и разные сроки жизни объектов. | Проверить постоянный Block и динамический Permit внутри одного собственного sublayer. |
| Собственный WFP callout | Требует драйвера для пользовательской логики классификации в ядре. | Исключён требованиями. |

Приоритет Block над Allow и отсутствие задаваемого администратором порядка обычных правил документированы Microsoft. Поэтому схема с постоянным запрещающим правилом Firewall и отдельным разрешающим правилом не решает задачу. Это не запрет на все возможные применения Firewall, а отказ от конкретной небезопасной схемы. [Windows Firewall rules](https://learn.microsoft.com/en-us/windows/security/operating-system-security/network-security/windows-firewall/rules).

В WFP внутри sublayer фильтры проверяются по весу до завершающего действия. Между sublayer действует отдельный арбитраж; soft permit оставляет другим политикам возможность запрета, hard permit может мешать запретам ниже по приоритету. Прототип не должен применять hard permit для обхода чужих правил. Также нельзя считать собственный Block безусловно сильнее любого фильтра стороннего провайдера. [Filter Arbitration](https://learn.microsoft.com/en-us/windows/win32/fwp/filter-arbitration).

## Схема WFP для прототипа

Следующая схема — проектное решение для проверки, а не подтверждённая гарантия безопасности:

1. Установщик создаёт собственные persistent provider и sublayer, а также постоянные блокирующие фильтры для каждого зарегистрированного App ID PowerShell.
2. Проверяются оба семейства адресов и оба направления установления соединений: `ALE_AUTH_CONNECT_V4/V6` и `ALE_AUTH_RECV_ACCEPT_V4/V6`. Только исходящий Connect не покрывает PowerShell, принимающий входящее соединение.
3. Во время подтверждённого разрешения создаются динамические soft permit с большим весом в том же sublayer. Условия разрешения должны ограничивать проверенный путь настолько, насколько это допускают выбранные слои.
4. Постоянные Block не удаляются и не отключаются для разрешения. При отзыве удаляются только динамические Permit.
5. Изменения группы собственных фильтров выполняются транзакционно. При ошибке любого обязательного шага транзакция отменяется; нельзя фиксировать частично подготовленное разрешение.
6. После изменения перечитываются собственные объекты, их условия и флаги. Ошибка чтения означает неизвестное состояние применения политики, а не успешную блокировку.

Постоянные объекты переживают завершение создавшего процесса. Объекты динамической сессии удаляются при её завершении; завершение процесса закрывает сессию через механизм RPC. Документация не задаёт для этого нулевую задержку. Транзакции WFP позволяют атомарно менять набор объектов. [Object Management](https://learn.microsoft.com/en-us/windows/win32/fwp/object-management).

Набор доступных условий различается по слоям. Для каждого Permit необходимо отдельно проверить наличие App ID, локального адреса и условий интерфейса, включая значения при повторной авторизации. Недоступное поле нельзя считать автоматически совпавшим с проверенным маршрутом. [Условия на слоях WFP](https://learn.microsoft.com/en-us/windows/win32/fwp/filtering-conditions-available-at-each-filtering-layer).

## Загрузка Windows и состояние BFE

Boot-time фильтры работают от старта TCP/IP до инициализации BFE, persistent-фильтры — после инициализации. Microsoft описывает атомарный переход между этими видами политики у одного провайдера. Это описание само по себе не подтверждает пригодность конкретного boot-time фильтра с App ID на нужном слое. [WFP Operation](https://learn.microsoft.com/en-us/windows/win32/fwp/basic-operation).

Флаги `BOOTTIME` и `PERSISTENT` нельзя объединить в одном фильтре: нужны отдельные объекты. В справке `FWPM_FILTER0` описан также флаг `DISABLED`, зависящий от связи провайдера со службой. Формулировка отличается от условий загрузки объектов в разделе Object Management. Поэтому загрузка собственного провайдера без service association требует отдельного испытания. Создавать фиктивную службу или присваивать себе чужую службу нельзя. [FWPM_FILTER0](https://learn.microsoft.com/en-us/windows/win32/api/fwpmtypes/ns-fwpmtypes-fwpm_filter0).

До проверки остаются открытыми:

- Возможность адресной boot-time блокировки только зарегистрированных PowerShell без воздействия на другие приложения.
- Реальное включение persistent-фильтров провайдера без собственного Windows Service.
- Поведение при остановке, аварии и восстановлении BFE во время работы ОС. Сохранность объекта в хранилище не доказывает непрерывность фильтрации.

Автозапуск приложения при входе пользователя не закрывает эти вопросы. Общая блокировка всех приложений на время загрузки неприемлема.

## Привилегии приложения с треем

Чтение состояния, изменение конфигурации и управление WFP должны иметь разные границы полномочий. Право открыть WFP-сессию не означает право добавлять фильтры. WFP проверяет права на контейнеры, объекты и транзакции; ACL только собственного фильтра недостаточно для всех операций создания. [WFP Access control](https://learn.microsoft.com/en-us/windows/win32/fwp/access-control).

| Модель | Оценка |
| --- | --- |
| Весь GUI с повышением прав | Проста для изолированного прототипа, но увеличивает объём привилегированного кода. Не выбрана как окончательная модель. |
| Обычный GUI и отдельный повышенный процесс без Windows Service | Предпочтительный кандидат по минимизации привилегий. Требует защищённого IPC и доказанного отзыва разрешения после смерти GUI. |
| Широкие права WFP для обычных пользователей | Не принимать: это расширяет возможность менять политику за пределами IPGuard. |

Установку базовой политики и её удаление выполнять с административными правами. Окончательную runtime-модель выбрать после проверки прав и жизненного цикла. Не вводить второй процесс только для вида: он должен уменьшать полномочия GUI и сохранять требования fail-closed.

Если используется помощник, он не принимает от GUI произвольные команды WFP или безусловное «разрешить». Проверяются права клиента, версия протокола и допустимые операции. Изменяемые непривилегированным пользователем файлы не должны позволять подменить доверенную политику или код. Правила завершения помощника при смерти GUI, разрыве IPC, logoff и смене пользовательской сессии входят в прототип. Heartbeat с таймаутом даёт задержку обнаружения и не равен немедленному отзыву.

У нескольких запущенных экземпляров не должно быть независимых Permit: один оставшийся процесс не должен сохранять разрешение после выхода другого владельца политики. Область владения политикой и взаимодействие с несколькими пользовательскими сессиями проверяются отдельно.

## Остановка и установленные соединения

| Событие | Требуемое поведение | Что нужно доказать |
| --- | --- | --- |
| Закрытие окна | Скрыть окно, продолжить контроль в трее. | WFP-сессия не закрыта по событию окна. |
| Явный выход | Отозвать Permit, проверить состояние, завершить приложение. | Новые соединения не проходят после отзыва. |
| Аварийное завершение владельца WFP-сессии | Динамические Permit исчезают, постоянные Block остаются. | Поведение новых и существующих потоков, задержка удаления. |
| Зависание процесса | Не выдавать бесконечно действующее разрешение на основании старой проверки. | Динамическая сессия при зависании не обязана завершаться; требуется отдельное решение. |
| Изменение сети | Аннулировать результат проверки и отозвать Permit. | Гонки между событием, проверкой и применением разрешения. |

Для ALE документирована повторная авторизация потока при изменении фильтров: после обнаружения изменения политики повторно проверяется первый проходящий пакет соответствующего потока. Это не обещание немедленного TCP RST или закрытия сокета в приложении. Проверяются TCP, UDP, оба направления и семейства адресов. [ALE Reauthorization](https://learn.microsoft.com/en-us/windows/win32/fwp/ale-re-authorization).

Нельзя обещать нулевое окно между физическим изменением сети и его обработкой пользовательским процессом. Измеряются отдельно задержка обнаружения, задержка отзыва и переданные после события данные. При невозможности выполнить обязательную гарантию это ограничение блокирует выпуск, а не скрывается настройкой.

## Определение внешнего выхода

`GetBestRoute2` возвращает локальный маршрут и исходный адрес для конкретного назначения. Он не сообщает внешний адрес после NAT. Индекс интерфейса может измениться после отключения и включения адаптера. Сравнивать нужно актуальные снимки сети, а не сохранённый однажды индекс. [GetBestRoute2](https://learn.microsoft.com/en-us/windows/win32/api/netioapi/nf-netioapi-getbestroute2).

Даже штатный Windows force tunnel опирается на маршруты: более специфичный физический маршрут может обойти маршрут VPN по умолчанию. Наличие VPN или двух default route не доказывает отсутствие split tunneling. [VPN routing decisions](https://learn.microsoft.com/en-us/windows/security/operating-system-security/network-security/vpn/vpn-routing).

Вывод для политики IPGuard: конечное число внешних проверок наблюдает только использованные пути. Оно не исключает NAT, прокси или маршрутизацию у провайдера, зависящие от назначения и протокола. Без внешне контролируемого и технически обеспеченного выхода нельзя объявлять общий выход доказанным. Добавлять вымышленный признак `TrustedRoute=true`, заменяющий эту проверку, нельзя.

| Сетевая ситуация | Решение до доказательства безопасности |
| --- | --- |
| Обычный NAT, несколько согласованных HTTPS-ответов | Адрес наблюдён, общий выход не доказан; Block. |
| Split tunnel, per-app VPN или неизвестный фильтрующий VPN | Block с причиной неподтверждённого пути. |
| Системный, пользовательский, переменный окружения или локальный прокси | Не переносить географию прокси на весь трафик PowerShell; Block при неопределённости. |
| IPv4 подтверждён, доступный IPv6 не подтверждён | Не разрешать непроверенное семейство; первоначальная общая политика остаётся Block. |
| Единственный видимый интерфейс | Сам по себе не доказывает единственный внешний адрес. |
| Проверка завершилась после изменения сети | Отбросить результат и проверить новую сеть под блокировкой. |

У HTTPS-проверок нужно явно исключать неявное использование прокси: у `HttpClientHandler.UseProxy` значение по умолчанию — `true`. Управляемый выбор сокета можно реализовать через `SocketsHttpHandler.ConnectCallback`, но он контролирует соединение проверяющего приложения, а не все соединения PowerShell. [UseProxy](https://learn.microsoft.com/en-us/dotnet/api/system.net.http.httpclienthandler.useproxy?view=net-10.0), [ConnectCallback](https://learn.microsoft.com/en-us/dotnet/api/system.net.http.socketshttphandler.connectcallback?view=net-10.0).

Источники публичного IP должны быть независимыми по оператору; два URL одного оператора не являются двумя независимыми источниками. Для IPv4 и IPv6 отдельно проверяются публичность адреса, таймауты, TLS и согласие ответов. Пока общий путь не доказан, GeoIP со страной US недостаточен для разрешения. Сам HTTPS не доказывает честность ответа источника.

Локальная GeoIP-база определяет страну в рамках своего покрытия и актуальности. Она не доказывает физическое местонахождение компьютера. Выбор формата и первый адаптер описаны ниже; отсутствие пригодной базы даёт Block. Обновление должно проходить проверку до атомарной замены рабочей базы.

## Локальная GeoIP — 2026-10-24

Для следующего шага обновления выбран DB-IP Country Lite: публичная месячная база IPv4/IPv6 в MMDB с `country.iso_code`. Провайдер указывает CC BY 4.0 и требование attribution; Lite имеет ограничения точности и покрытия. Это выбор источника, а не доказательство страны для конкретного адреса. Продукт ещё не загружает и не распространяет рабочую базу; attribution в интерфейсе/поставке нужно включить до распространения данных. [DB-IP Country Lite](https://db-ip.com/db/download/ip-to-country-lite), [схема MMDB](https://db-ip.com/db/format/ip-to-country-lite/mmdb.html).

Для декодирования закреплён официальный MaxMind.Db 5.2.0 (Apache-2.0), имеющий net10.0 target без дополнительных package dependencies. Используется композиция с Reader, не собственный MMDB-парсер. Дата сборки берётся из Metadata.BuildDate. Документированный конструктор со Stream создаёт приватный снимок. API и пакет исследованы до реализации; после этого реальный decoder проверен синтетическими fixtures. [пакет 5.2.0](https://www.nuget.org/packages/MaxMind.Db/5.2.0), [исходники reader](https://github.com/maxmind/MaxMind-DB-Reader-dotnet/tree/v5.2.0), [формат MMDB](https://maxmind.github.io/MaxMind-DB/).

Адаптер принимает country products DBIP-Country-Lite, GeoLite2-Country и GeoIP2-Country, format 2.0, IPVersion 6. Последнее обязательно, чтобы отсутствие IPv6 в файле не превратилось в ложное подтверждение. Реальная база провайдера пока не проверена end to end: тесты используют GeoIP2-Country-Test, отдельно отклоняют City. Наличие метаданных допустимого типа не аутентифицирует файл и не подтверждает все записи. Полный FindAll по недоверенной базе не выполняется; ошибку позднего lookup нужно обрабатывать как отказ всего снимка.

Один FileStream открыт с FileShare.Read: на Windows это запрещает совместное открытие для записи. Проверяется размер 1..64 MiB, вычисляется SHA-256, тот же handle перематывается и передаётся reader; исходный файл затем закрывается. Снимок остаётся неизменным после замены файла. SHA-256 устанавливает идентичность загруженных байтов, но не доверие поставщику; проверка происхождения относится к updater. Время файловой системы и время скачивания не участвуют в свежести. Эксклюзивный deadline — build timestamp + заданный maximumAge; возраст ещё не задан глобальной конфигурацией и передаётся вызывающим кодом.

Lookup синхронный и использует явный now. Открытие должно выполняться вне UI-потока; вызывающий сценарий обязан продлить общий интервал NetworkAssessment через lookup и заново проверить время и поколение перед публикацией. Reader использует тот же snapshot публичных диапазонов, что HTTPS parser. Только country.iso_code даёт страну; registered_country, represented_country и continent не заменяют отсутствующие данные. Проверяется канонический формат двух ASCII-заглавных букв и отклоняются XX/ZZ/EU/AP. Это проверка схемы и известных placeholders, а не независимое подтверждение точности GeoIP. Любая неразрешённая страна остаётся отрицательным решением Domain.

Операционная ошибка чтения сохраняет исходное исключение и навсегда закрывает возможность положительного lookup в этом экземпляре. Ошибки конструктора освобождают уже переданный decoder; двойная ошибка открытия/cleanup сохраняет обе причины. Dispose синхронизирован с чтением, идемпотентен и запрещает последующие обращения к decoder. Прежняя успешная страна после отказа не используется. Это fail-closed для данных, а не реализация сетевой блокировки.

Для воспроизводимых тестов добавлены небольшие synthetic MMDB из MaxMind-DB на закреплённом commit, с provenance и MIT license. Проверены различающиеся country/registered_country, отсутствие страны при наличии registered_country, IPv4/IPv6, повреждение, размер, устаревание и замена источника при живом снимке. Рабочая база DB-IP не включена в репозиторий или EXE. [источник fixtures](https://github.com/maxmind/MaxMind-DB/tree/255b9a8b8a692d70dcaef31dc2ca44fa7ce50ece).

Обновление реализовано шагом 6b, описанным ниже, а сборка NetworkAssessment — шагом 6c. Ошибка или прерванное обновление не должны разрешать сеть либо освежать старые данные.

### Обновление DB-IP — 2026-10-24

Граница доверия — конкретный провайдер через системную HTTPS-проверку hostname/certificate: download.db-ip.com и путь /free/dbip-country-lite-UTC-yyyy-MM.mmdb.gz. Redirect, proxy, cookies и автоматическая декомпрессия отключены; прочие хосты, порты, query, fragment и неподходящий путь отклоняются до запроса. Это не независимая криптографическая подпись данных. На странице провайдера есть MD5/SHA1, но они не используются как доказательство происхождения. Получение более старого месяца после ошибки не выполняется. Источник и условия данных: [DB-IP](https://db-ip.com/db/download/ip-to-country-lite).

Лимиты: 16 MiB compressed, 64 MiB decoded; Content-Length не заменяет фактический счётчик. Принимается только HTTP 200 с binary gzip/octet-stream Content-Type и без Content-Encoding. Общий timeout охватывает transfer, чтение тела, распаковку и запись в stage. Проверяются CRC-32 и ISIZE из полного gzip trailer, в том числе отдельный случай отсутствующего trailer. Использован System.IO.Hashing 10.0.12 вместо собственного CRC-алгоритма. CRC обнаруживает повреждение архива, не аутентифицирует поставщика. [GZipStream](https://learn.microsoft.com/en-us/dotnet/api/system.io.compression.gzipstream?view=net-10.0), [System.IO.Hashing](https://www.nuget.org/packages/System.IO.Hashing/10.0.12).

Публикация: новая stage рядом с active file, FileMode.CreateNew/FileShare.None, flushToDisk, открытие настоящим MMDB reader и проверка product/build/freshness. Metadata проверяется полностью в пределах существующего контракта, но весь набор записей не обходится. Поздняя ошибка lookup по-прежнему делает снимок непригодным. SHA-256 и build date старого файла образуют rollback floor: более старый build и отличающиеся байты с той же датой отклоняются. Повтор тех же свежих байтов не меняет mtime или deadline. Повреждённый либо недоступный active file нельзя считать отсутствующим: такой отказ прекращает update и требует явного восстановления.

Для согласованных writers используется постоянный .update.lock с эксклюзивным открытым handle. Сам файл после закрытия не удаляется: иначе разные процессы могли бы открыть разные файловые идентичности под тем же именем. Перед commit ещё раз проверяются active digest, время и cancellation. Cancellation после последней проверки может пересечься с commit; успешное переименование возвращает успех, без последующего throw по token. Обычный отказ до commit сохраняет active file и удаляет только stage этой операции. Старые orphan stages не принимаются за active и не удаляются автоматически. Вызов обязан использовать существующий доверенный локальный каталог с защищёнными ACL; проверки reparse points не устраняют гонки в каталоге, доступном чужому writer.

Для commit выбран File.Move(stage, target, overwrite: true) в одном каталоге, без copy/delete/truncate fallback. File.Replace исследован отдельно: у ReplaceFileW документированы некоторые состояния ошибки с изменившимися именами, а WRITE_THROUGH не поддерживается. Не обещается универсальная транзакция с восстановлением после отключения питания. Проверены нормальное переименование и отказ при запрете delete sharing на Windows local files. Network shares, иные файловые системы и crash injection во время commit не валидированы. [File.Move](https://learn.microsoft.com/en-us/dotnet/api/system.io.file.move?view=net-10.0), [ReplaceFileW](https://learn.microsoft.com/en-us/windows/win32/api/winbase/nf-winbase-replacefilew).

### Сборка оценки сети — 2026-10-24

NetworkAssessor в Application соединяет существующий PublicIpCollector, фабрику локальной IGeoIpCountryDatabase и PublicIpPolicy. Windows, MMDB, HTTP и GUI в сценарий не добавлены. Новый factory-owned снимок используется для всех lookup одной оценки и закрывается до финального checkpoint. Валидность источников определяет общий PublicIpConsensus в Domain; общий CheckInterval в PublicIpPolicy владеет порядком времени и exclusive age limit. Проверка совпадения снимков сети общая для collector и assessor. Это извлечение уже используемых правил, без нового механизма доверия к маршруту.

Checkpoint повторно захватывает сеть, читает время, проверяет caller cancellation и исходный latch. Проверяются version, обе доступности и token identity. Возраст отсчитывается от начала HTTPS-сбора, а не окончания lookup; каждое новое время сравнивается с предыдущим. Срок проверяется до local work, после открытия, после каждого lookup и после cleanup. Исходные наблюдения не теряются: несогласованные/неудачные ответы остаются в Domain и диагностике, но адрес такой семьи не передаётся GeoIP. При обоих недоступных семействах или отсутствии согласованного адреса база не открывается, положительного решения нет.

Весь интервал включает opening/lookup/disposal. App проверяет consistency database type/build/deadline/hash и привязку lookup к запрошенному адресу/deadline, а успешные страны оценивает существующая Domain policy. Отрицательный lookup, future/stale metadata, ошибка открытия/чтения или invalid adapter result не возвращают Snapshot. Сохраняются collection attempts, database metadata, валидированный отказ lookup и исходное исключение; ошибки lookup + cleanup сохраняются вместе. Caller cancellation имеет приоритет над возвращаемым результатом.

Дополнительный TDD-случай: faulty adapter меняет IPAddress.ScopeId. До исправления сравнение с уже изменённым объектом пропускало adapter mismatch, возвращая Completed с отрицательным Domain.GeoIpAddressMismatch. Теперь строка исходного адреса фиксируется до вызова adapter и результат помечается InvalidGeoIpResult. Это защита привязки, а не утверждение, что adapter независимо подтверждает страну.

Completed означает текущую завершённую оценку данных, а не доступ к сети. Snapshot содержит Evidence, предварительный Decision и живой NetworkSnapshot.Invalidated. Следующий потребитель обязан повторить проверку поколения/сигнала/времени и Domain evaluation: последнее чтение сети не предотвращает будущую смену. Публикация обновлённой базы также не переписывает уже полученный снимок; scheduler/lifecycle должны инициировать новую оценку. Общий выход PowerShell всё ещё не доказан, Permit не открывается, реального Windows monitor пока нет.

9 безопасных интеграционных случаев соединяют настоящий PublicIpReader и MMDB decoder со сценарием/Domain на synthetic fixture и controlled HTTP. Проверены разные страны семейств (US/JP), unknown/registered-only country, unavailable IPv6, missing/corrupt database, источник файла, заменённый между lookup, и invalidation после настоящего lookup. Публичные источники IP, реальные GeoIP-download и mutating Firewall/WFP API не вызываются. Непроверенный live monitor остаётся этапом 7.

### Реализация динамической сессии — 2026-10-23

Для шага 3b повторно сверены `FWPM_SESSION_FLAG_DYNAMIC`, флаги фильтра и арбитраж. Прототип создаёт непостоянный Permit с весом 20 над постоянным Block с весом 10 в том же собственном sublayer; `FWPM_FILTER_FLAG_CLEAR_ACTION_RIGHT` не применяется. Это не обход чужих Block. `WfpPermitLease` проверяет весь baseline перед добавлением первого Permit в одной транзакции и держит динамическую сессию открытой после фиксации. Отзыв закрывает её, не удаляя постоянные Block. Поэтому принято консервативное решение: больше не передавать его в нативные вызовы, сохранить ошибку и повторно сообщать её при последующих `Dispose`. В VM потребуется проверить завершение процесса-владельца и фактическую очистку через RPC rundown; ошибка закрытия не считается успешным отзывом. [FwpmEngineClose0](https://learn.microsoft.com/en-us/windows/win32/api/fwpmu/nf-fwpmu-fwpmengineclose0).

Тесты используют fake-сессии и fake close-функции, без реального открытия динамической WFP-сессии и без записи политики. `IsClosed` не означает сетевую блокировку, отсутствие другого владельца Permit или разрыв установленных соединений. Автоматическое удаление при смерти процесса, задержка RPC rundown, зависание, несколько владельцев и срок свежести разрешения остаются непроверенными условиями W04/W05/W09/W12/W23. Подключать этот API как рабочий режим Allow до их закрытия нельзя.

### Прототип удаления политики — 2026-10-23

Удаление выполняется в одной write-транзакции в порядке «фильтры → sublayer → provider». Объект со ссылками из других объектов удалить нельзя; эта ошибка не обходится и вызывает откат. Удаление через динамическую сессию для постоянных объектов не используется. Это следует из ограничений времени жизни и порядка ссылок WFP. [Object Management](https://learn.microsoft.com/en-us/windows/win32/fwp/object-management), [Uninstalling a Provider](https://learn.microsoft.com/en-us/windows/win32/fwp/uninstalling-a-provider).

Для удаления нужен свежий enumerator в той же транзакции. Null template по справке запрашивает все фильтры, но API возвращает только доступные вызывающему для чтения объекты. Поэтому отсутствие объекта в перечислении не считается доказательством отсутствия всех зависимостей. Удаление контейнеров остаётся обязательным и не игнорирует ошибки ссылок или доступа. Страницы обходятся по 128 записей; освобождается массив страницы, а не каждый отдельный указатель. Ошибка обхода, освобождения enumerator или закрытия сессии не скрывает исходную ошибку. [FwpmFilterCreateEnumHandle0](https://learn.microsoft.com/en-us/windows/win32/api/fwpmu/nf-fwpmu-fwpmfiltercreateenumhandle0), [FwpmFilterEnum0](https://learn.microsoft.com/en-us/windows/win32/api/fwpmu/nf-fwpmu-fwpmfilterenum0).

Отбор проверяет собственные provider/sublayer GUID, маркер схемы, постоянство, Block, вес, слой, единственное условие App ID и прежний формат ключа. Совпадение отображаемого имени недостаточно. Для удаления можно распознать собственный disabled-объект, но это не делает его активным фильтром. Permit и неизвестные связанные объекты приводят к отказу. App ID копируется из снимка, поэтому исполняемый файл может уже отсутствовать. После каждого нативного delete проверяется отсутствие объекта по ключу; удаление не является обычным отзывом Permit.

Unit-тесты используют fake-сессии и локально выделенную память. Нативные перечисление, delete, поведение `FWP_E_IN_USE`, readback в write-транзакции и откат в реальном BFE пока не проверены. Эта реализация остаётся прототипом и не заменяет установщик или деинсталлятор продукта.

### Подготовка режима VM — 2026-10-23

Для обычного запуска используется динамический skip xUnit v3 до входа в callback с WFP-операциями. Условия допуска проверяются на подставленных данных; отрицательные проверки действительно проходят как тесты, а не учитываются как skips. Права проверяются по эффективному токену `WindowsPrincipal.IsInRole(Administrator)`, без запроса UAC; ошибка чтения токена не разрешает запуск. [xUnit v3 dynamic skipping](https://xunit.net/docs/getting-started/v3/whats-new), [WindowsPrincipal.IsInRole](https://learn.microsoft.com/en-us/dotnet/api/system.security.principal.windowsprincipal.isinrole?view=net-10.0).

Явные подтверждения оператора связаны с именем машины и существующим снимком. Сам факт аппаратной виртуализации не доказывает изоляцию; скрипт не притворяется, что может проверить сетевую схему и checkpoint из гостя. CI и отсутствие любого условия приводят к отказу до создания правил. Прямой `dotnet test` по умолчанию пропускает единственный mutating test; скрипт VM считает такой skip неуспешным испытанием.

Первый нативный сценарий ограничен объектами для приватной копии PowerShell. Предварительная проверка отвергает даже частичные существующие контейнеры, чтобы тест не принял чужую или старую установку за свою. Снимки полей фильтров читаются в read-only транзакциях и сохраняются в журнал; память страниц остаётся действительной только внутри callback. В случае ошибки выдачи или отзыва дальнейшее удаление baseline не выполняется. Реальные сетевые гарантии, crash/RPC rundown и сроки свежести остаются открытыми: этот сценарий пока не запускался и не измеряет пакеты.

В рабочей среде командой `dotnet --info` подтверждены SDK 10.0.401 и Windows build 26100, win-x64. На момент этапа 1 исходных проектов ещё не было, поэтому сборка и xUnit-тесты к исследованию неприменимы. Сетевые правила, BFE, автозапуск и права ОС при исследовании не менялись. Реализация оболочки описана в результате этапа 2 в [плане](implementation-plan.md).

Поддержку нельзя объявлять для любой редакции Windows 10/11. Матрица .NET 10 привязана к версиям и жизненному циклу ОС; совместимость Avalonia и фактические испытания должны дополнительно сузить матрицу выпуска. [Поддерживаемые ОС .NET 10](https://github.com/dotnet/core/blob/main/release-notes/10.0/supported-os.md).

Исследование завершено как анализ документации и рисков. Решения для прототипа и проверяемые критерии определены. Реальная пригодность WFP без службы ещё не подтверждена: boot-time адресность, активация провайдера, отзыв разрешений, runtime-привилегии, новые пути PowerShell и доказательство общего внешнего выхода остаются условиями приёмки. Можно продолжать безопасную реализацию и тесты домена, но нельзя выпускать разрешающий режим до закрытия этих вопросов.
