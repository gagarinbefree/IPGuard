# Техническое исследование IPGuard

Дата проверки источников: 22–27 октября 2026 года.

## Защищённый helper, шаг 8b.3b — 27 октября 2026 года

Helper использует существующий EXE с явным режимом до Avalonia, но только из фиксированной защищённой folder installation. Один runas не удостоверяет executable или конфигурацию. Поэтому launcher принимает живой ProtectedHelperInstallation, а не произвольный путь; parent PID берётся из текущего процесса, pipe name ограничен прежним форматом. Helper повторяет проверку установки, удерживает Process GUI и затем проверяет kernel-bound pipe и тот же account. Alternate-account elevation по-прежнему не поддерживается. UseShellExecute не перенаправляет stdio; launcher возвращает Process и передаёт UAC errors caller. Native UAC в этой среде не запускался. [Shell verbs](https://learn.microsoft.com/en-us/windows/win32/shell/launch), [ArgumentList](https://learn.microsoft.com/en-us/dotnet/api/system.diagnostics.processstartinfo.argumentlist?view=net-10.0).

CreateFileW вызывается с OPEN_REPARSE_POINT и BACKUP_SEMANTICS, GetFileInformationByHandle проверяет actual attributes и link count, GetSecurityInfo читает actual owner/DACL. Проверка не делает второй path-based read конфигурации. Все ancestors/dependencies удерживаются до конца session: directories не разделяют delete, files — write/delete. Проверка parent ACL до открытия child и отказ reparse защищают этот проход от замены непривилегированным writer; это модель против обычного пользователя, не администратора. Для ancestor запрещены чужие delete/delete-child/WRITE_DAC/WRITE_OWNER, для самой установки — также data/attribute writes. InheritOnly не даёт доступа текущему object; unsupported effective ACE отвергается. При deny/allow combinations возможен консервативный отказ, сложное вычисление effective ACL не добавлено. Владельцы/writers ограничены SY/BA/TrustedInstaller. Предел 512 объектов ограничивает обход; files с несколькими hard links отвергаются. Это выбранная политика приложения, не стандартная гарантия любых Windows ACL. [CreateFile flags/sharing](https://learn.microsoft.com/en-us/windows/win32/api/fileapi/nf-fileapi-createfilea), [File security/access](https://learn.microsoft.com/en-us/windows/win32/fileio/file-security-and-access-rights), [Handle metadata](https://learn.microsoft.com/en-us/windows/win32/api/fileapi/ns-fileapi-by_handle_file_information).

Single-file native extraction происходит до Main и обычно использует TEMP/.net; Microsoft требует недоступный для principals с другими привилегиями extraction directory. Поэтому bundle не считается разрешённым elevated deployment: пустой Assembly.Location отвергается сознательно, с локальным обоснованным IL3000 suppression. Launcher из portable application не получает trusted installation. Для VM нужен защищённый folder publish, а не переименованный release EXE. Installer, runtime/environment loading review и фактические mixed-elevation checks ещё нужны; эти guards не превращают уже запущенный недоверенный EXE в безопасный. [Single-file extraction and security](https://learn.microsoft.com/en-us/dotnet/core/deploying/single-file/).

Protected helper.json ограничен 16 KiB, version 1, 1–32 local PowerShell paths и whole-second interval 1–3600. Это block-only scope, не полная конфигурация будущего приложения. Запрещены дополнительные поля/duplicate keys, remote/device paths, mutable exposed scope, пустой/невалидный список. Helper не получает scope по IPC, не делает PowerShell discovery и не выдаёт Permit. Local diagnostics используют реальные Windows readers, но public-IP/GeoIP composition пока не подключена. Перед IPC выполняется initial reconcile; startup connection failure проходит тот же final reconciliation/cleanup/owner release. Отсутствие installer baseline по-прежнему не даёт pre-logon/boot гарантий. Shutdown и WFP native calls могут быть uninterruptible; срок команды не означает принудительный native abort.

Safe tests проверяют schema/ACL/arguments на synthetic data, read-only native security и sharing на уникальном временном файле, fake-backend runtime с настоящими bound pipes, отказ uninstalled entry и routing неизвестных аргументов без GUI. Production mutex, native WFP enumeration/write, UAC, installed-layout mutation и elevated bundle не запускались. Положительный safe CI не подтверждает сетевой enforcement или готовность к установке на рабочей машине.

IPGuard будет настольным приложением с треем на .NET 10, Avalonia, Avalonia.Markup.Declarative и CommunityToolkit.Mvvm. Собственный Windows Service и драйвер ядра исключены. Для прототипа выбран пользовательский API WFP. Пригодность схемы для выпуска зависит от испытаний, перечисленных в [программе проверок VM](vm-validation.md).

Основной риск — различие между наблюдением адреса и обеспечением маршрута: несколько HTTPS-ответов с адресом США не доказывают, что произвольное соединение PowerShell использует тот же внешний выход. При отсутствии достаточного подтверждения решение остаётся блокирующим. Геолокация адреса удалённого сервера в принятии решения не участвует.

## Команды и lifecycle, шаг 8b.3a — 27 октября 2026 года

После process-bound transport добавлен отдельный bounded command protocol. JSON length проверяется до allocation: request максимум 256 bytes, reply 4096 bytes, prefix unsigned big-endian uint32. Читатель ожидает ровно заявленный body; EOF и partial frame не превращаются в Status. Schema version обязательна. System.Text.Json настроен на Disallow unmapped members, запрет duplicate properties, required constructor parameters и nullable annotations, MaxDepth=4. Requests содержат только version и exact command string. Response не десериализует native exceptions, delegates, tokens или полиморфные объекты. Используются API установленного .NET 10 reference pack без нового package. [Unmapped fields](https://learn.microsoft.com/en-us/dotnet/standard/serialization/system-text-json/missing-members), [Duplicates](https://learn.microsoft.com/en-us/dotnet/api/system.text.json.jsonserializeroptions.allowduplicateproperties?view=net-10.0), [Constructor parameters](https://learn.microsoft.com/en-us/dotnet/api/system.text.json.jsonserializeroptions.respectrequiredconstructorparameters?view=net-10.0).

IPC API block-only: status, recheck, stop. File paths/configuration payload, Permit и Uninstall отсутствуют. Reply — diagnostic last observation, не capability для сети; nullable inspection, counts и UTC observation time проходят общий application contract. HasError сообщает об ошибке без передачи приватного exception text. Network observations с cancellation tokens и полноценные IP/GeoIP details этим минимальным reply пока не передаются.

ProtectionRuntime сохраняет owner до завершения controller.StopAsync, diagnostics cleanup и native drain. Caller cancellation отменяет только waiting. Consumer cached reader вызывается вне runtime gate: test воспроизвёл deadlock-like timeout при host-side Stop на другом потоке, после исправления Capture возвращает terminal state. Cleanup пытается пройти все границы после обычной exception и агрегирует ошибки; hung native call не прерывается и не считается завершённым.

Command session закрывается после EOF, invalid data, idle timeout, cancellation или явного Stop; transport retire выполняется перед потенциально долгой final reconciliation. Final cleanup использует независимый lifetime. Explicit Stop reply отправляется только после shutdown и содержит HasError при неудачной cleanup; отсутствие reply не доказывает, что helper не выполнил запрос. Client после любого interrupted started transaction закрывает channel; поздний reply не может стать ответом следующего call. Queued cancellation не затрагивает active exchange. Синхронный Windows API и уже начатое backend действие не имеют real-time cancellation guarantee.

Для будущего UAC launch подходит shell verb runas; consent может быть отклонён, а UseShellExecute несовместим со стандартным redirected-process IPC. Поэтому уже выбран named pipe, а параметры должны формироваться через ArgumentList, не строковую shell-команду. Но runas сам по себе не удостоверяет содержимое executable, scope или конфигурацию. До автоматического launcher нужны реальный helper entry point и защищённые executable/configuration paths; этот шаг не повышает произвольный путь из GUI и не запускает обычный Desktop с несуществующим helper mode. [ShellExecute runas](https://learn.microsoft.com/en-us/windows/win32/api/shellapi/nf-shellapi-shellexecutew), [UseShellExecute](https://learn.microsoft.com/en-us/dotnet/api/system.diagnostics.processstartinfo.useshellexecute?view=net-10.0), [ArgumentList](https://learn.microsoft.com/en-us/dotnet/api/system.diagnostics.processstartinfo.argumentlist?view=net-10.0).

Тесты соединяют real bound pipes с fake policy boundary и не включают UAC/WFP. Policy runtime, protocol errors и teardown подтверждены в этой композиции; действительная блокировка пакетов, Windows boot coverage, helper crash/hang и cross-elevation остаются isolated VM work. Desktop ещё не использует session API.

## Локальный IPC, шаг 8b.2 — 27 октября 2026 года

Для следующего hosting выбран GUI-owned named pipe: обычный GUI создаёт listener до запуска helper, повышенный helper подключается как client. Направление важно для mandatory integrity checks; обратное соединение с high-integrity server не считается проверенным. PipeOptions.CurrentUserOnly проверяет не только user account, но и elevation level, поэтому не подходит как готовая граница между обычным GUI и повышенным helper. Реализован transport; UAC startup и команды пока не подключены. [PipeOptions](https://learn.microsoft.com/en-us/dotnet/api/system.io.pipes.pipeoptions?view=net-10.0).

Каждый listener имеет новый `IPGuard.Control.<guid>` name, FirstPipeInstance, maxInstances=1, byte mode, asynchronous I/O и non-inheritable handle. Protected DACL содержит deny FullControl для Network SID и allow ReadWrite/Synchronize для GUI logon SID и enabled Administrators; owner — GUI user SID. Data-only Administrators ACE нужен для linked elevated token с другим logon SID; CreateNewInstance не разрешён ни одному client principal. Default DACL не используется: он может разрешать Everyone/anonymous reads. Для client запрашиваются individual PipeAccessRights.ReadWrite с отсутствующим CreateNewInstance, а не GENERIC_WRITE, включающий FILE_CREATE_PIPE_INSTANCE. Logon SID ограничивает доступ текущим входом, а не всем входам того же пользователя. DACL проверяется после server creation и на подключившемся client до передачи marker; unsafe descriptor не исправляется. Remote logon, другая сессия и mixed-elevation UAC pair ещё требуют VM-проверки. [Named Pipe Security and Access Rights](https://learn.microsoft.com/en-us/windows/win32/ipc/named-pipe-security-and-access-rights), [Create](https://learn.microsoft.com/en-us/dotnet/api/system.io.pipes.namedpipeserverstreamacl.create?view=net-10.0), [Client constructors](https://learn.microsoft.com/en-us/dotnet/api/system.io.pipes.namedpipeclientstream.-ctor?view=net-10.0).

WindowsIdentity.Groups намеренно исключает logon-ID groups: первоначальный поиск через это свойство воспроизвёл отказ всех listeners. Исправление использует GetTokenInformation(TokenLogonSid) с TOKEN_QUERY. TOKEN_GROUPS ограничен 1024 bytes, ожидается ровно одна enabled non-deny-only logon group; pointer и полный SID должны помещаться в буфере. SID копируется в managed memory, allocation всегда освобождается. Никакого fallback на общий user SID при ошибке нет. [Runtime source, pinned v10.0.0](https://github.com/dotnet/runtime/blob/v10.0.0/src/libraries/System.Security.Principal.Windows/src/System/Security/Principal/WindowsIdentity.cs), [GetTokenInformation](https://learn.microsoft.com/en-us/windows/win32/api/securitybaseapi/nf-securitybaseapi-gettokeninformation), [TOKEN_INFORMATION_CLASS](https://learn.microsoft.com/en-us/windows/win32/api/winnt/ne-winnt-token_information_class), [TOKEN_GROUPS](https://learn.microsoft.com/en-us/windows/win32/api/winnt/ns-winnt-token_groups).

UAC создаёт связанные logon sessions, поэтому равенство logon SID не предполагается. Client читает token доверенного GUI process через OpenProcessToken(TOKEN_QUERY), требует совпадения user SID и строит ожидаемый descriptor по GUI logon SID, а не по своему. Alternate-account elevation не поддерживается. [Linked logon sessions](https://learn.microsoft.com/en-us/troubleshoot/windows-client/networking/mapped-drives-not-available-from-elevated-command).

Обе стороны проверяют kernel-reported peer PID через GetNamedPipeClientProcessId/GetNamedPipeServerProcessId по переданному retained live Process. Уже завершившийся peer отвергается до connection wait; после handshake PID/liveness проверяются снова. Caller обязан получить Process от доверенного launcher и удерживать его handle; произвольный PID из входного сообщения не является доверенным peer. Проверка PID не доказывает binary integrity, повышение прав или защищённость от вмешательства того же пользователя/администратора. Происхождение executable, его защищённая установка и elevated token остаются обязанностью будущего launcher/host. [Client PID](https://learn.microsoft.com/en-us/windows/win32/api/winbase/nf-winbase-getnamedpipeclientprocessid), [Server PID](https://learn.microsoft.com/en-us/windows/win32/api/winbase/nf-winbase-getnamedpipeserverprocessid).

Client использует TokenImpersonationLevel.Identification: сервер может определить его личность, но не выполнять действия с правами клиента. Safe integration test читает фактический impersonation level через RunAsClient и подтверждает Identification. После peer checks передаётся только фиксированный 18-byte `IPGuard.Control/1` marker с newline; это version check, не секрет и не самостоятельная аутентификация. Неизвестная версия/EOF/partial data/отмена не возвращают stream. Connection и handshake имеют общий timeout 1 ms–1 minute, проверяемый также перед передачей stream. [Identification](https://learn.microsoft.com/en-us/dotnet/api/system.security.principal.tokenimpersonationlevel?view=net-10.0). Синхронные token/ACL/process native reads не прерываются cancellation: hosting должен выполнять их вне UI thread и не обещать абсолютный wall-clock deadline для зависшего Windows API. Успех передаёт владение stream caller; failed authentication закрывает one-shot listener. Automatic reconnect отсутствует.

Transport не содержит file paths/configuration messages, WFP operations, UAC launch или auto-start. Command protocol и runtime lifecycle поверх него добавлены в шаге 8b.3a выше. Тесты transport создают только уникальные pipes и hidden unprivileged PowerShell children; один child реально проходит server PID binding и duplex byte exchange. Endpoint collision, unsafe ACL, unexpected process, stalled/unsupported peer и cleanup проверяются без изменения Firewall/WFP. Защита от process hang и настоящий privileged hosting ещё не подтверждены.

## Межпроцессное владение, шаг 8b.1 — 27 октября 2026 года

Для координации cooperating runtime processes выбран именованный kernel mutex `Global\IPGuard.PolicyOwner.v1`. Global namespace виден между пользовательскими сессиями; Local namespace недостаточен для общей WFP-политики. Это соглашение участников, а не запрет другим программам обращаться к WFP и не защита от администратора. GUI пока не захватывает этот объект. [Kernel Object Namespaces](https://learn.microsoft.com/en-us/windows/win32/termserv/kernel-object-namespaces).

Mutex принадлежит acquiring thread: освобождение из произвольного async continuation недопустимо. WindowsPolicyOwner держит его на dedicated background thread, без polling и ожидания contention: Busy возвращает null. AbandonedMutexException означает успешный захват после прекращения прежнего owner thread; WasAbandoned служит диагностикой, baseline всегда требует новой сверки. Нельзя доверять прежним readback или permits. RequestStop сначала отзывает ownership latch, затем worker освобождает mutex и закрывает handle. Consumer callbacks выполняются асинхронно и не задерживают native release; callback может сам ожидать DisposeAsync. [Mutex](https://learn.microsoft.com/en-us/dotnet/api/system.threading.mutex), [Mutex Objects](https://learn.microsoft.com/en-us/windows/win32/sync/mutex-objects).

Public acquisition требует Windows x64 и enabled Administrators token; UAC автоматически не запускается. Это prerequisite выбранного hosting design, не доказательство доступа к WFP: реальные access checks остаются в WFP API. Новый mutex получает owner Builtin Administrators и protected DACL с FullControl только для Administrators и LocalSystem. MutexAcl.Create применяет descriptor только при создании: при открытии existing object всегда проверяется фактический owner/DACL, включая type, flags, mask и точный набор ACE. Неподходящий descriptor или collision отвергаются без исправления чужого объекта. Squatting может вызвать отказ запуска, но не выдачу доступа. .NET 10 предоставляет необходимые ACL API без дополнительной PackageReference; явная зависимость была отвергнута restore как ненужная (NU1510) и удалена. [MutexAcl.Create](https://learn.microsoft.com/en-us/dotnet/api/system.threading.mutexacl.create), [GetAccessControl](https://learn.microsoft.com/en-us/dotnet/api/system.threading.threadingaclextensions.getaccesscontrol), [WindowsPrincipal.IsInRole](https://learn.microsoft.com/en-us/dotnet/api/system.security.principal.windowsprincipal.isinrole).

OwnedBlockPolicy принимает ownership lease и сериализует вызовы существующего IBlockPolicy. Caller cancellation не освобождает owner. При потере ownership новый вызов не входит в backend, late result отбрасывается. Dispose запрещает новые/queued calls, ждёт возврата uninterruptible native operation и только затем освобождает owner один раз. Хост обязан сначала дождаться BlockProtectionController.StopAsync, затем закрыть OwnedBlockPolicy. Неправильный порядок не считается финальной сверкой. Backend без wrapper остаётся доступен для VM experiments; новый механизм сам по себе не делает prototype Permit пригодным для runtime.

Safe integration tests используют только уникальные `Global\IPGuard.Tests.Owner.<guid>` objects: настоящий child process демонстрирует contention, normal release и process-death abandonment. Отдельно проверяются rejection без ACL rewrite и protected creation при текущем token (либо явный отказ standard token). На локальном standard token MutexAcl вернул IOException с HRESULT 0x8007051B: ERROR_INVALID_OWNER (1307). Это конкретный отказ назначить owner, не условно принимаемая произвольная IO failure; успешное elevated создание локально не проверялось. [System Error Codes](https://learn.microsoft.com/en-us/windows/win32/debug/system-error-codes--1300-1699-). Эти проверки не открывают WFP и не меняют сеть. Privileged helper executable, authenticated IPC/UAC lifecycle, hang handling, installer/boot recovery и реальная VM enforcement остаются следующими шагами.

## Блокирующая координация — 27 октября 2026 года

WFP поддерживает read-only и read/write transactions с ACID semantics. Строгая runtime-инспекция может использовать существующий read-only ownership/schema preflight, не вызывая удаления: все его нативные операции — Get/Enum. Для actual uninstall по-прежнему нужна одна write transaction, содержащая проверку и удаление. Проверка наличия отдельных Block не доказывает отсутствие более приоритетных Permit в том же sublayer; strict inspection сверяет также related namespace. [Object Management](https://learn.microsoft.com/en-us/windows/win32/fwp/object-management), [Transaction Begin](https://learn.microsoft.com/en-us/windows/win32/api/fwpmu/nf-fwpmu-fwpmtransactionbegin0), [Filter Arbitration](https://learn.microsoft.com/en-us/windows/win32/fwp/filter-arbitration).

Access checks для open, read/write transactions, Get/Enum и Add различаются; успешное открытие сессии не доказывает право установить фильтры. Windows adapter не требует безусловный admin boolean и не меняет ACL: фактические WFP access errors сохраняются. Автоматическое повышение GUI и новый IPC не добавлены без выбранного/проверенного runtime design. [Access Control](https://learn.microsoft.com/en-us/windows/win32/fwp/access-control).

Application controller умеет только persistent baseline ensure/readback и terminal reconciliation. Он не открывает динамическую session и не вызывает prototype Permit/Uninstall. Stop не отменяет уже выполняющийся native write; ждёт его и проводит собственную финальную сверку. Отмена ожидания UI не прекращает эту работу. Хост должен отдельно остановить diagnostics, организовать periodic policy checks и single process owner. Ошибки/зависания BFE, права реального runtime account, загрузка Windows, process-crash и actual traffic остаются VM-вопросами. Last-observed objects/time намеренно не называются доказанной effective blocking.

Новые тесты используют in-memory WFP boundary, а не настоящие native writes/enum. Existing Permit сохраняется как conflict; forced cleanup отсутствует. После остановки географические snapshots не используются, late results не возвращают Running state. Финальные ensure/readback errors агрегируются, а retired diagnostic error не загрязняет завершённую сверку политики.

## Мониторинг и диагностика Windows — 24–27 октября 2026 года

### Полный периодический цикл, шаг 7c.2 — 27 октября

Добавлена композиция local observations и public IP/GeoIP с общими outer generation, interval и final policy. Синхронные local/native/MMDB calls по-прежнему требуют background host; async метод сам по себе не переносит их с UI thread. Существующий monitor запускает сценарий на worker и ожидает HTTPS attempts. Локальный monitor OS не обнаруживает NAT-only изменения; повторные full checks получают новые внешние адреса без OS event. До завершения следующего успешного запроса текущий внешний адрес не известен достоверно, а checks не доказывают общий выход PowerShell.

Earliest deadline фактического GeoIP evidence ограничивает и cached validation, и timer published observation. Deadline вооружается после final validation только если сокращает оставшийся исходный elapsed limit. Timer callbacks зависят от runtime scheduling; held snapshot не является разрешением и требует перепроверки tokens/time перед использованием. Clock rollback проверяется на каждом boundary и через containment child intervals: локально обнаружен и исправлен случай, когда route child завершался позже последующего parent timestamp, но оба значения оставались после общего старта.

Runtime loop не продублирован: local-only и full collection используют внутренний общий контракт; реальные platform boundaries не менялись. Ошибки публичных sources остаются в полном ordered attempt list и дают negative decision, а DB/operational failures сохраняются в diagnostic-only Assessment и LastFailure без outer Snapshot. Общая политика по-прежнему не содержит Allow или TrustedRoute и не вызывает WFP. Новых пакетов и платформенных API этот шаг не добавляет.

### Общий локальный цикл, шаг 7c.1

Сочетание generation token и UTC interval не делает последовательные route/proxy/RAS reads атомарной транзакцией ОС. Сборщик проверяет обе границы, исходный latch и shared domain CheckInterval после каждого reader; Unknown family не мешает диагностике, но не становится public-IP eligibility. Для proxy/RAS без уведомлений добавлен отдельный periodic refresh. В шаге 7c.1 HTTPS/GeoIP в локальный цикл ещё не входил; общая композиция появилась в шаге 7c.2 выше.

TimeProvider предоставляет timers и timestamp-based elapsed measurement. Deadline вооружается до collection, а не после завершения; Capture и публикация проверяют также elapsed age независимо от UTC и доставки timer callback. Таймеры не являются real-time enforcement: scheduling может задерживать callback, полученный immutable object сам себя удалить не может. Перед использованием нужны оба live tokens и freshness; WFP этот цикл не меняет. [CreateTimer](https://learn.microsoft.com/en-us/dotnet/api/system.timeprovider.createtimer?view=net-10.0), [GetElapsedTime](https://learn.microsoft.com/en-us/dotnet/api/system.timeprovider.getelapsedtime?view=net-10.0).

CancelAsync синхронно устанавливает cancellation latch, а callbacks выполняет асинхронно; их ошибки нужно наблюдать. CancellationTokenRegistration.Unregister, в отличие от Dispose, не ждёт уже выполняющийся callback. Это позволяет отзывать данные под короткой блокировкой без ожидания reentrant consumers. Источник хранится до завершения reader и callbacks. Dispose цикла не ждёт uninterruptible native call; Completion позволяет хосту дождаться worker отдельно. [CancelAsync](https://learn.microsoft.com/en-us/dotnet/api/system.threading.cancellationtokensource.cancelasync?view=net-10.0), [Unregister](https://learn.microsoft.com/en-us/dotnet/api/system.threading.cancellationtokenregistration.unregister?view=net-10.0).

Unit-тесты используют официальный FakeTimeProvider 10.9.0, только в UnitTests; runtime dependency или собственный наследник TimeProvider не добавлен. Barriers управляют interleaving reads; bounded real watchdog используется только для ожидания тестового результата, а не как модель periodic time. Проверены TTL, refresh без generation change, повторные запросы, ошибка после успеха, reconnect на новой generation, late response, exit во время чтения, callback exceptions и reentrant refresh/dispose. [FakeTimeProvider](https://learn.microsoft.com/en-us/dotnet/api/microsoft.extensions.time.testing.faketimeprovider), [Package](https://www.nuget.org/packages/Microsoft.Extensions.TimeProvider.Testing/10.9.0).

### Proxy и RAS, шаг 7b.2

WinHttpGetIEProxyConfigForCurrentUser возвращает active-connection settings текущего пользователя, включая auto-detect/PAC; missing settings — ошибка, не Direct. WinHttpGetDefaultProxyConfiguration читает legacy registry defaults, которые не отражают session overrides. В адаптере эти данные не смешиваются с текущими HTTP_PROXY/HTTPS_PROXY/ALL_PROXY/NO_PROXY. Сохраняются только flags; proxy/PAC/bypass strings не декодируются в результат. PAC/WPAD не вызываются. [User proxy](https://learn.microsoft.com/en-us/windows/win32/api/winhttp/nf-winhttp-winhttpgetieproxyconfigforcurrentuser), [WinHTTP defaults](https://learn.microsoft.com/en-us/windows/win32/api/winhttp/nf-winhttp-winhttpgetdefaultproxyconfiguration).

Все возвращённые string pointers освобождаются GlobalFree, включая partial native results и cancellation. Попытки cleanup продолжаются после ошибки отдельного allocation; alias pointers не освобождаются дважды. Ненулевой return GlobalFree — failure; primary/cleanup errors агрегируются, результата нет. Неудачный GlobalFree не объявляется успешным освобождением; возможная оставшаяся память не переиспользуется адаптером. [GlobalFree](https://learn.microsoft.com/en-us/windows/win32/api/winbase/nf-winbase-globalfree).

RasEnumConnectionsW перечисляет active RAS связи, но не все реализации VPN; соединение может ещё не попасть в enumeration до успешного подключения. Для каждого заимствованного handle выполняется RasGetConnectStatusW; API error и status.dwError различаются. Адаптер ничего не dial/hang-up и не закрывает HRASCONN. Device type "vpn" — только положительная классификация этой RAS записи. Empty list не превращается в NoVPN. Correlation GUID сохраняется при наличии; RAS LUID относится к logon session, не NET_LUID интерфейса, и для route join не используется. [Enumeration](https://learn.microsoft.com/en-us/windows/win32/api/ras/nf-ras-rasenumconnectionsw), [Status](https://learn.microsoft.com/en-us/windows/win32/api/ras/nf-ras-rasgetconnectstatusw), [RASCONN](https://learn.microsoft.com/en-us/previous-versions/windows/desktop/legacy/aa376725%28v%3Dvs.85%29).

При RASCS_Connected субсостояния IKEv2 Dormant и Reconnecting не объявляются Connected в диагностической модели. Unknown raw values сохраняются, connection error даёт Failed. RASCSS_Reconnected считается Connected после завершения MOBIKE, при этом исходный substate code сохраняется. [RASCONNSUBSTATE](https://learn.microsoft.com/en-us/previous-versions/windows/desktop/legacy/dd408103%28v%3Dvs.85%29), [RASCONNSTATUS](https://learn.microsoft.com/en-us/previous-versions/windows/desktop/legacy/aa376728%28v%3Dvs.85%29).

Локальный clang-cl probe Windows SDK 10.0.26100.0 x64 подтвердил RAS pack=4: RASCONNW 1388 bytes, handle offset 4, device type 526 (17 UTF-16 code units), correlation GUID 1372; RASCONNSTATUSW 608 bytes, substate offset 604. WinHTTP user struct — 32 bytes, default — 24, первые pointer members имеют offset 8 после четырёхбайтового BOOL/DWORD. Полные native buffers зарезервированы; private phonebook/phone/endpoint fields не представлены в результатах. Эти значения защищены layout-тестом; C++ не нужен для сборки проекта.

RAS allocation ограничен 1024 entries и четырьмя attempts, рост/ошибочные размеры проверяются до обхода; все caller-owned buffers освобождаются в finally. Это пределы нашего adapter, не Windows. OS calls синхронны и не прерываются CancellationToken; отмена проверяется на границах. Настройки, enumeration и status не являются одной транзакцией или доказанным network generation. Standalone readers не дают lifetime guarantees; в шаге 7c.1 они объединены interval/generation-bound collector и periodic monitor. Proxy-only изменения и per-app/session overrides могут не дать network notification. Settings/Connected — не подтверждение общего public exit или WFP enforcement; настоящие VPN disconnect/reconnect остаются испытаниями VM.

### Локальная таблица маршрутов, шаг 7b.1

Read-only адаптер использует GetIpForwardTable2 с AF_UNSPEC и отдельно GetIpInterfaceEntry для каждой уникальной пары family/interface. Route metric — только offset; interface metric хранится отдельно, сумма вычисляется в ulong, неопределённый компонент не превращается в числовой приоритет. Сохраняются не только defaults, но и specific routes, scoped IPv6 next hop, on-link/loopback, connection/default-route flags и remaining lifetime. Это данные диагностики, не выбор гарантированного выхода. [GetIpForwardTable2](https://learn.microsoft.com/en-us/windows/win32/api/netioapi/nf-netioapi-getipforwardtable2), [MIB_IPFORWARD_ROW2](https://learn.microsoft.com/en-us/windows/win32/api/netioapi/ns-netioapi-mib_ipforward_row2), [MIB_IPINTERFACE_ROW](https://learn.microsoft.com/en-us/windows/win32/api/netioapi/ns-netioapi-mib_ipinterface_row).

Windows SDK 10.0.26100.0 проверен отдельным локальным clang-cl x64 layout probe: SOCKADDR_INET — 28 bytes/align 4, MIB_IPFORWARD_ROW2 — 104/align 8, первая строка таблицы начинается с offset 8, MIB_IPINTERFACE_ROW — 168/align 8. Route prefix находится по offset 12, prefix length 40, next hop 44, route metric 84. Interface metric находится по offset 148, Connected 156, DisableDefaultRoutes 166. Эти значения защищены unit-тестом и настоящими read-only вызовами; C++ не становится зависимостью сборки решения.

Нативная таблица принадлежит IP Helper и освобождается целиком через FreeMibTable, не по отдельным строкам. Число строк ограничено 65,536 перед обходом; это предел диагностического адаптера, не лимит Windows. API не возвращает длину allocation, поэтому проверка count не является валидацией произвольного указателя из недоверенного источника. Отказ любой строки/interface отбрасывает весь результат; read и cleanup errors не подменяют друг друга. Синхронный OS call не прерывается CancellationToken; отмена проверяется между вызовами, строками и после cleanup. [FreeMibTable](https://learn.microsoft.com/en-us/windows/win32/api/netioapi/nf-netioapi-freemibtable), [GetIpInterfaceEntry](https://learn.microsoft.com/en-us/windows/win32/api/netioapi/nf-netioapi-getipinterfaceentry).

RouteDiagnosticsCollector связывает копию данных с двумя captures monitor и живым generation latch, дополнительно проверяет latch после clock callback и отбрасывает clock rollback. Native table и interface metadata не читаются в одной транзакции, а OS notification может задержаться: snapshot означает одно наблюдаемое поколение, не атомарную картину ядра. Empty table, отсутствие IPv6, disconnected или истёкшая строка не доказывают отсутствие других путей. Данные не меняют IpFamilyAvailability и не дают WFP Permit.

GetCurrentThreadCompartmentId в актуальной справке Microsoft помечен «Do not use this function»; Get/SetSessionCompartmentId и SetCurrentThreadCompartmentId также reserved. Они не используются, и обход compartments не имитируется изменением контекста потока. Coverage адаптера ограничен local caller context, полный охват остаётся неподтверждённым. Proxy, per-app VPN, source-bound routing, NAT exit и split tunneling ещё требуют самостоятельной диагностики и enforcement. [GetCurrentThreadCompartmentId](https://learn.microsoft.com/en-us/windows/win32/api/netioapi/nf-netioapi-getcurrentthreadcompartmentid), [Netioapi API index](https://learn.microsoft.com/en-us/windows/win32/api/netioapi/).

В рабочей Windows проверены реальные route/interface read, повторное чтение после освобождения буфера и привязка к monitor latch. Настоящие изменения маршрутов/VPN не генерировались. В TDD найдено, что IPNetwork.TryParse нормализует host bits: адаптер дополнительно сравнивает исходный адрес с разобранной base address и отклоняет malformed IPv4/IPv6 prefix. Это наблюдение теста .NET 10, а не предположение о строгом поведении parser.

### Подписки и поколения сети, шаг 7a

Для этапа 7a выбраны три независимые read-only подписки IP Helper: [NotifyRouteChange2](https://learn.microsoft.com/en-us/windows/win32/api/netioapi/nf-netioapi-notifyroutechange2), [NotifyIpInterfaceChange](https://learn.microsoft.com/en-us/windows/win32/api/netioapi/nf-netioapi-notifyipinterfacechange) и [NotifyUnicastIpAddressChange](https://learn.microsoft.com/en-us/windows/win32/api/netioapi/nf-netioapi-notifyunicastipaddresschange). AF_UNSPEC подписывает IPv4 и IPv6. BOOLEAN передаётся одним байтом, ADDRESS_FAMILY — двумя. InitialNotification=false: подтверждение регистрации не является изменением. Общий callback принимает только сигнал; чужая row-память не читается и не удерживается. Регистрация всех трёх выполняется до первого чтения интерфейсов.

Windows запрещает вызывать отмену с потока того же callback и предупреждает о взаимных блокировках через удерживаемые ресурсы. Поэтому CancelMibChangeNotify2 вызывается без gate монитора и вне callback stack; дополнительный guard отклоняет прямую отмену из собственного callback. Успех отмены освобождает root делегата; при ошибке отменяются остальные подписки, ошибка сообщается, оставшийся handle и GC-root сохраняются для повторного Dispose. Неудачная инициализация с неудачной очисткой сохраняет обе ошибки и удерживает нативный root до завершения процесса. Это консервативное управление памятью, а не успешная очистка. [CancelMibChangeNotify2](https://learn.microsoft.com/en-us/windows/win32/api/netioapi/nf-netioapi-cancelmibchangenotify2).

Старый cached snapshot очищается под gate одновременно с увеличением revision. CancellationTokenSource.CancelAsync синхронно устанавливает IsCancellationRequested, но запускает consumer callbacks асинхронно; их исключения агрегируются. Это позволяет потребителю вызвать Capture/Dispose без входа в нативную отмену на callback stack. Отмена наблюдается отдельной задачей, CTS освобождается после окончания callbacks. Dispose не ждёт произвольного consumer, который сам может закрывать монитор. [CancellationTokenSource.CancelAsync](https://learn.microsoft.com/en-us/dotnet/api/system.threading.cancellationtokensource.cancelasync?view=net-10.0).

Сериализованный фоновый reader использует GetAllNetworkInterfaces и локальные unicast-адреса. Available означает лишь наличие candidate для HTTPS-пробы на Up non-loopback интерфейсе; private IPv4 и link-local IPv6 не объявляются публичным выходом. Отсутствие candidate остаётся Unknown, не Unavailable: неполный обзор интерфейсов не доказывает отсутствие семейства во всех compartments или у конкретного приложения. IPv4-only конфигурация из-за этого не проходит полную оценку. Ошибка чтения сохраняет null snapshot. Ошибка notification latch не может быть скрыта уже поставленным в очередь refresh; повтор разрешается явно через Refresh. [GetAllNetworkInterfaces](https://learn.microsoft.com/en-us/dotnet/api/system.net.networkinformation.networkinterface.getallnetworkinterfaces?view=net-10.0), [GetIPProperties](https://learn.microsoft.com/en-us/dotnet/api/system.net.networkinformation.networkinterface.getipproperties?view=net-10.0).

В рабочей Windows реально проверены только чтение и registration/cancellation, без сетевых изменений. Controlled callbacks проверяют все три категории, отмену работающего PublicIpCollector и latch завершённой GeoIP-оценки. Это не испытание настоящих route-only изменений, VPN disconnect/reconnect, split tunneling, proxy-only изменений или всех compartments. NAT public-IP смена без локальных изменений требует периодических HTTPS-проверок. Scheduler, route/proxy/VPN inventory и подключение GUI ещё не реализованы. Уведомления ОС асинхронны и сами не отзывают WFP Permit или установленные соединения; будущая оркестрация должна повторно проверять поколение, возраст и факт применения политики.

## Выбор механизма фильтрации

| Вариант | Возможности и ограничения | Решение |
| --- | --- | --- |
| Обычные правила Windows Firewall | Явный Block перекрывает конфликтующий Allow. Отключённый на время разрешения Block сам не восстанавливается при падении GUI. | Не использовать как основу временного разрешения с fail-closed. |
| Пользовательский API WFP | Есть собственные sublayer, веса фильтров, транзакции и разные сроки жизни объектов. | Проверить постоянный Block и динамический Permit внутри одного собственного sublayer. |
| Собственный WFP callout | Требует драйвера для пользовательской логики классификации в ядре. | Исключён требованиями. |

Приоритет Block над Allow и отсутствие задаваемого администратором порядка обычных правил документированы Microsoft. Поэтому схема с постоянным запрещающим правилом Firewall и отдельным разрешающим правилом не решает задачу. Это не запрет на все возможные применения Firewall, а отказ от конкретной небезопасной схемы. [Windows Firewall rules](https://learn.microsoft.com/en-us/windows/security/operating-system-security/network-security/windows-firewall/rules).

В WFP внутри sublayer фильтры проверяются по весу до завершающего действия. Между sublayer действует отдельный арбитраж; soft permit оставляет другим политикам возможность запрета, hard permit может мешать запретам ниже по приоритету. Прототип не должен применять hard permit для обхода чужих правил. Также нельзя считать собственный Block безусловно сильнее любого фильтра стороннего провайдера. [Filter Arbitration](https://learn.microsoft.com/en-us/windows/win32/fwp/filter-arbitration).

## Схема WFP для прототипа

Следующая схема — проектное решение для проверки, а не подтверждённая гарантия безопасности:

1. Установщик создаёт собственные persistent provider и sublayer, а также постоянные блокирующие фильтры для каждого зарегистрированного App ID PowerShell.
2. Проверяются оба семейства адресов и оба направления установления соединений: `ALE_AUTH_CONNECT_V4/V6` и `ALE_AUTH_RECV_ACCEPT_V4/V6`. Только исходящий Connect не покрывает PowerShell, принимающий входящее соединение.
3. Во время подтверждённого разрешения создаются динамические soft permit с большим весом в том же sublayer. Условия разрешения должны ограничивать проверенный путь настолько, насколько это допускают выбранные слои.
4. Постоянные Block не удаляются и не отключаются для разрешения. При отзыве удаляются только динамические Permit.
5. Изменения группы собственных фильтров выполняются транзакционно. При ошибке любого обязательного шага транзакция отменяется; нельзя фиксировать частично подготовленное разрешение.
6. После изменения перечитываются собственные объекты, их условия и флаги. Ошибка чтения означает неизвестное состояние применения политики, а не успешную блокировку.

Постоянные объекты переживают завершение создавшего процесса. Объекты динамической сессии удаляются при её завершении; завершение процесса закрывает сессию через механизм RPC. Документация не задаёт для этого нулевую задержку. Транзакции WFP позволяют атомарно менять набор объектов. [Object Management](https://learn.microsoft.com/en-us/windows/win32/fwp/object-management).

Набор доступных условий различается по слоям. Для каждого Permit необходимо отдельно проверить наличие App ID, локального адреса и условий интерфейса, включая значения при повторной авторизации. Недоступное поле нельзя считать автоматически совпавшим с проверенным маршрутом. [Условия на слоях WFP](https://learn.microsoft.com/en-us/windows/win32/fwp/filtering-conditions-available-at-each-filtering-layer).

## Загрузка Windows и состояние BFE

Boot-time фильтры работают от старта TCP/IP до инициализации BFE, persistent-фильтры — после инициализации. Microsoft описывает атомарный переход между этими видами политики у одного провайдера. Это описание само по себе не подтверждает пригодность конкретного boot-time фильтра с App ID на нужном слое. [WFP Operation](https://learn.microsoft.com/en-us/windows/win32/fwp/basic-operation).

Флаги `BOOTTIME` и `PERSISTENT` нельзя объединить в одном фильтре: нужны отдельные объекты. В справке `FWPM_FILTER0` описан также флаг `DISABLED`, зависящий от связи провайдера со службой. Формулировка отличается от условий загрузки объектов в разделе Object Management. Поэтому загрузка собственного провайдера без service association требует отдельного испытания. Создавать фиктивную службу или присваивать себе чужую службу нельзя. [FWPM_FILTER0](https://learn.microsoft.com/en-us/windows/win32/api/fwpmtypes/ns-fwpmtypes-fwpm_filter0).

До проверки остаются открытыми:

- Возможность адресной boot-time блокировки только зарегистрированных PowerShell без воздействия на другие приложения.
- Реальное включение persistent-фильтров провайдера без собственного Windows Service.
- Поведение при остановке, аварии и восстановлении BFE во время работы ОС. Сохранность объекта в хранилище не доказывает непрерывность фильтрации.

Автозапуск приложения при входе пользователя не закрывает эти вопросы. Общая блокировка всех приложений на время загрузки неприемлема.

## Привилегии приложения с треем

Чтение состояния, изменение конфигурации и управление WFP должны иметь разные границы полномочий. Право открыть WFP-сессию не означает право добавлять фильтры. WFP проверяет права на контейнеры, объекты и транзакции; ACL только собственного фильтра недостаточно для всех операций создания. [WFP Access control](https://learn.microsoft.com/en-us/windows/win32/fwp/access-control).

| Модель | Оценка |
| --- | --- |
| Весь GUI с повышением прав | Проста для изолированного прототипа, но увеличивает объём привилегированного кода. Не выбрана как окончательная модель. |
| Обычный GUI и отдельный повышенный процесс без Windows Service | Предпочтительный кандидат по минимизации привилегий. Требует защищённого IPC и доказанного отзыва разрешения после смерти GUI. |
| Широкие права WFP для обычных пользователей | Не принимать: это расширяет возможность менять политику за пределами IPGuard. |

Установку базовой политики и её удаление выполнять с административными правами. Окончательную runtime-модель выбрать после проверки прав и жизненного цикла. Не вводить второй процесс только для вида: он должен уменьшать полномочия GUI и сохранять требования fail-closed.

Если используется помощник, он не принимает от GUI произвольные команды WFP или безусловное «разрешить». Проверяются права клиента, версия протокола и допустимые операции. Изменяемые непривилегированным пользователем файлы не должны позволять подменить доверенную политику или код. Правила завершения помощника при смерти GUI, разрыве IPC, logoff и смене пользовательской сессии входят в прототип. Heartbeat с таймаутом даёт задержку обнаружения и не равен немедленному отзыву.

У нескольких запущенных экземпляров не должно быть независимых Permit: один оставшийся процесс не должен сохранять разрешение после выхода другого владельца политики. Область владения политикой и взаимодействие с несколькими пользовательскими сессиями проверяются отдельно.

## Остановка и установленные соединения

| Событие | Требуемое поведение | Что нужно доказать |
| --- | --- | --- |
| Закрытие окна | Скрыть окно, продолжить контроль в трее. | WFP-сессия не закрыта по событию окна. |
| Явный выход | Отозвать Permit, проверить состояние, завершить приложение. | Новые соединения не проходят после отзыва. |
| Аварийное завершение владельца WFP-сессии | Динамические Permit исчезают, постоянные Block остаются. | Поведение новых и существующих потоков, задержка удаления. |
| Зависание процесса | Не выдавать бесконечно действующее разрешение на основании старой проверки. | Динамическая сессия при зависании не обязана завершаться; требуется отдельное решение. |
| Изменение сети | Аннулировать результат проверки и отозвать Permit. | Гонки между событием, проверкой и применением разрешения. |

Для ALE документирована повторная авторизация потока при изменении фильтров: после обнаружения изменения политики повторно проверяется первый проходящий пакет соответствующего потока. Это не обещание немедленного TCP RST или закрытия сокета в приложении. Проверяются TCP, UDP, оба направления и семейства адресов. [ALE Reauthorization](https://learn.microsoft.com/en-us/windows/win32/fwp/ale-re-authorization).

Нельзя обещать нулевое окно между физическим изменением сети и его обработкой пользовательским процессом. Измеряются отдельно задержка обнаружения, задержка отзыва и переданные после события данные. При невозможности выполнить обязательную гарантию это ограничение блокирует выпуск, а не скрывается настройкой.

## Определение внешнего выхода

`GetBestRoute2` возвращает локальный маршрут и исходный адрес для конкретного назначения. Он не сообщает внешний адрес после NAT. Индекс интерфейса может измениться после отключения и включения адаптера. Сравнивать нужно актуальные снимки сети, а не сохранённый однажды индекс. [GetBestRoute2](https://learn.microsoft.com/en-us/windows/win32/api/netioapi/nf-netioapi-getbestroute2).

Даже штатный Windows force tunnel опирается на маршруты: более специфичный физический маршрут может обойти маршрут VPN по умолчанию. Наличие VPN или двух default route не доказывает отсутствие split tunneling. [VPN routing decisions](https://learn.microsoft.com/en-us/windows/security/operating-system-security/network-security/vpn/vpn-routing).

Вывод для политики IPGuard: конечное число внешних проверок наблюдает только использованные пути. Оно не исключает NAT, прокси или маршрутизацию у провайдера, зависящие от назначения и протокола. Без внешне контролируемого и технически обеспеченного выхода нельзя объявлять общий выход доказанным. Добавлять вымышленный признак `TrustedRoute=true`, заменяющий эту проверку, нельзя.

| Сетевая ситуация | Решение до доказательства безопасности |
| --- | --- |
| Обычный NAT, несколько согласованных HTTPS-ответов | Адрес наблюдён, общий выход не доказан; Block. |
| Split tunnel, per-app VPN или неизвестный фильтрующий VPN | Block с причиной неподтверждённого пути. |
| Системный, пользовательский, переменный окружения или локальный прокси | Не переносить географию прокси на весь трафик PowerShell; Block при неопределённости. |
| IPv4 подтверждён, доступный IPv6 не подтверждён | Не разрешать непроверенное семейство; первоначальная общая политика остаётся Block. |
| Единственный видимый интерфейс | Сам по себе не доказывает единственный внешний адрес. |
| Проверка завершилась после изменения сети | Отбросить результат и проверить новую сеть под блокировкой. |

У HTTPS-проверок нужно явно исключать неявное использование прокси: у `HttpClientHandler.UseProxy` значение по умолчанию — `true`. Управляемый выбор сокета можно реализовать через `SocketsHttpHandler.ConnectCallback`, но он контролирует соединение проверяющего приложения, а не все соединения PowerShell. [UseProxy](https://learn.microsoft.com/en-us/dotnet/api/system.net.http.httpclienthandler.useproxy?view=net-10.0), [ConnectCallback](https://learn.microsoft.com/en-us/dotnet/api/system.net.http.socketshttphandler.connectcallback?view=net-10.0).

Источники публичного IP должны быть независимыми по оператору; два URL одного оператора не являются двумя независимыми источниками. Для IPv4 и IPv6 отдельно проверяются публичность адреса, таймауты, TLS и согласие ответов. Пока общий путь не доказан, GeoIP со страной US недостаточен для разрешения. Сам HTTPS не доказывает честность ответа источника.

Локальная GeoIP-база определяет страну в рамках своего покрытия и актуальности. Она не доказывает физическое местонахождение компьютера. Выбор формата и первый адаптер описаны ниже; отсутствие пригодной базы даёт Block. Обновление должно проходить проверку до атомарной замены рабочей базы.

## Локальная GeoIP — 2026-10-24

Для следующего шага обновления выбран DB-IP Country Lite: публичная месячная база IPv4/IPv6 в MMDB с `country.iso_code`. Провайдер указывает CC BY 4.0 и требование attribution; Lite имеет ограничения точности и покрытия. Это выбор источника, а не доказательство страны для конкретного адреса. Продукт ещё не загружает и не распространяет рабочую базу; attribution в интерфейсе/поставке нужно включить до распространения данных. [DB-IP Country Lite](https://db-ip.com/db/download/ip-to-country-lite), [схема MMDB](https://db-ip.com/db/format/ip-to-country-lite/mmdb.html).

Для декодирования закреплён официальный MaxMind.Db 5.2.0 (Apache-2.0), имеющий net10.0 target без дополнительных package dependencies. Используется композиция с Reader, не собственный MMDB-парсер. Дата сборки берётся из Metadata.BuildDate. Документированный конструктор со Stream создаёт приватный снимок. API и пакет исследованы до реализации; после этого реальный decoder проверен синтетическими fixtures. [пакет 5.2.0](https://www.nuget.org/packages/MaxMind.Db/5.2.0), [исходники reader](https://github.com/maxmind/MaxMind-DB-Reader-dotnet/tree/v5.2.0), [формат MMDB](https://maxmind.github.io/MaxMind-DB/).

Адаптер принимает country products DBIP-Country-Lite, GeoLite2-Country и GeoIP2-Country, format 2.0, IPVersion 6. Последнее обязательно, чтобы отсутствие IPv6 в файле не превратилось в ложное подтверждение. Реальная база провайдера пока не проверена end to end: тесты используют GeoIP2-Country-Test, отдельно отклоняют City. Наличие метаданных допустимого типа не аутентифицирует файл и не подтверждает все записи. Полный FindAll по недоверенной базе не выполняется; ошибку позднего lookup нужно обрабатывать как отказ всего снимка.

Один FileStream открыт с FileShare.Read: на Windows это запрещает совместное открытие для записи. Проверяется размер 1..64 MiB, вычисляется SHA-256, тот же handle перематывается и передаётся reader; исходный файл затем закрывается. Снимок остаётся неизменным после замены файла. SHA-256 устанавливает идентичность загруженных байтов, но не доверие поставщику; проверка происхождения относится к updater. Время файловой системы и время скачивания не участвуют в свежести. Эксклюзивный deadline — build timestamp + заданный maximumAge; возраст ещё не задан глобальной конфигурацией и передаётся вызывающим кодом.

Lookup синхронный и использует явный now. Открытие должно выполняться вне UI-потока; вызывающий сценарий обязан продлить общий интервал NetworkAssessment через lookup и заново проверить время и поколение перед публикацией. Reader использует тот же snapshot публичных диапазонов, что HTTPS parser. Только country.iso_code даёт страну; registered_country, represented_country и continent не заменяют отсутствующие данные. Проверяется канонический формат двух ASCII-заглавных букв и отклоняются XX/ZZ/EU/AP. Это проверка схемы и известных placeholders, а не независимое подтверждение точности GeoIP. Любая неразрешённая страна остаётся отрицательным решением Domain.

Операционная ошибка чтения сохраняет исходное исключение и навсегда закрывает возможность положительного lookup в этом экземпляре. Ошибки конструктора освобождают уже переданный decoder; двойная ошибка открытия/cleanup сохраняет обе причины. Dispose синхронизирован с чтением, идемпотентен и запрещает последующие обращения к decoder. Прежняя успешная страна после отказа не используется. Это fail-closed для данных, а не реализация сетевой блокировки.

Для воспроизводимых тестов добавлены небольшие synthetic MMDB из MaxMind-DB на закреплённом commit, с provenance и MIT license. Проверены различающиеся country/registered_country, отсутствие страны при наличии registered_country, IPv4/IPv6, повреждение, размер, устаревание и замена источника при живом снимке. Рабочая база DB-IP не включена в репозиторий или EXE. [источник fixtures](https://github.com/maxmind/MaxMind-DB/tree/255b9a8b8a692d70dcaef31dc2ca44fa7ce50ece).

Обновление реализовано шагом 6b, описанным ниже, а сборка NetworkAssessment — шагом 6c. Ошибка или прерванное обновление не должны разрешать сеть либо освежать старые данные.

### Обновление DB-IP — 2026-10-24

Граница доверия — конкретный провайдер через системную HTTPS-проверку hostname/certificate: download.db-ip.com и путь /free/dbip-country-lite-UTC-yyyy-MM.mmdb.gz. Redirect, proxy, cookies и автоматическая декомпрессия отключены; прочие хосты, порты, query, fragment и неподходящий путь отклоняются до запроса. Это не независимая криптографическая подпись данных. На странице провайдера есть MD5/SHA1, но они не используются как доказательство происхождения. Получение более старого месяца после ошибки не выполняется. Источник и условия данных: [DB-IP](https://db-ip.com/db/download/ip-to-country-lite).

Лимиты: 16 MiB compressed, 64 MiB decoded; Content-Length не заменяет фактический счётчик. Принимается только HTTP 200 с binary gzip/octet-stream Content-Type и без Content-Encoding. Общий timeout охватывает transfer, чтение тела, распаковку и запись в stage. Проверяются CRC-32 и ISIZE из полного gzip trailer, в том числе отдельный случай отсутствующего trailer. Использован System.IO.Hashing 10.0.12 вместо собственного CRC-алгоритма. CRC обнаруживает повреждение архива, не аутентифицирует поставщика. [GZipStream](https://learn.microsoft.com/en-us/dotnet/api/system.io.compression.gzipstream?view=net-10.0), [System.IO.Hashing](https://www.nuget.org/packages/System.IO.Hashing/10.0.12).

Публикация: новая stage рядом с active file, FileMode.CreateNew/FileShare.None, flushToDisk, открытие настоящим MMDB reader и проверка product/build/freshness. Metadata проверяется полностью в пределах существующего контракта, но весь набор записей не обходится. Поздняя ошибка lookup по-прежнему делает снимок непригодным. SHA-256 и build date старого файла образуют rollback floor: более старый build и отличающиеся байты с той же датой отклоняются. Повтор тех же свежих байтов не меняет mtime или deadline. Повреждённый либо недоступный active file нельзя считать отсутствующим: такой отказ прекращает update и требует явного восстановления.

Для согласованных writers используется постоянный .update.lock с эксклюзивным открытым handle. Сам файл после закрытия не удаляется: иначе разные процессы могли бы открыть разные файловые идентичности под тем же именем. Перед commit ещё раз проверяются active digest, время и cancellation. Cancellation после последней проверки может пересечься с commit; успешное переименование возвращает успех, без последующего throw по token. Обычный отказ до commit сохраняет active file и удаляет только stage этой операции. Старые orphan stages не принимаются за active и не удаляются автоматически. Вызов обязан использовать существующий доверенный локальный каталог с защищёнными ACL; проверки reparse points не устраняют гонки в каталоге, доступном чужому writer.

Для commit выбран File.Move(stage, target, overwrite: true) в одном каталоге, без copy/delete/truncate fallback. File.Replace исследован отдельно: у ReplaceFileW документированы некоторые состояния ошибки с изменившимися именами, а WRITE_THROUGH не поддерживается. Не обещается универсальная транзакция с восстановлением после отключения питания. Проверены нормальное переименование и отказ при запрете delete sharing на Windows local files. Network shares, иные файловые системы и crash injection во время commit не валидированы. [File.Move](https://learn.microsoft.com/en-us/dotnet/api/system.io.file.move?view=net-10.0), [ReplaceFileW](https://learn.microsoft.com/en-us/windows/win32/api/winbase/nf-winbase-replacefilew).

Отдельный ручной smoke, вне dotnet test: реальный HttpsGeoIpDownloadTransport → DbIpCountryDownloader → GeoIpDatabaseUpdater → MmdbCountryDatabase. Установлен DBIP-Country-Lite, 8 348 509 bytes, build 2026-10-01T01:36:12Z, maximumAge 45 days, deadline 2026-11-15T01:36:12Z. SHA-256 decoded MMDB: DBD70CCFA2A13627EAF4913D19920A1A229F1B3C5439AC01C509995B6364202A. Второй вызов получил Changed=false с теми же build/deadline/hash. Это наблюдение конкретного файла, не закрепление доверенного digest для будущих обновлений.

Lookup тестовых адресов 8.8.8.8 и 2001:4860:4860::8888 вернул Found с US и CA соответственно. Это не определение публичного адреса рабочей машины и не доказательство физического расположения Google или компьютера. Результат дополнительно показывает, почему страна одного семейства не переносится на другое. Загруженный файл находится только в игнорируемом локальном cache и не входит в source/release. README содержит attribution; отображение результатов в GUI потребует attribution в интерфейсе. GUI/CLI и scheduler пока не подключены.

### Сборка оценки сети — 2026-10-24

NetworkAssessor в Application соединяет существующий PublicIpCollector, фабрику локальной IGeoIpCountryDatabase и PublicIpPolicy. Windows, MMDB, HTTP и GUI в сценарий не добавлены. Новый factory-owned снимок используется для всех lookup одной оценки и закрывается до финального checkpoint. Валидность источников определяет общий PublicIpConsensus в Domain; общий CheckInterval в PublicIpPolicy владеет порядком времени и exclusive age limit. Проверка совпадения снимков сети общая для collector и assessor. Это извлечение уже используемых правил, без нового механизма доверия к маршруту.

Checkpoint повторно захватывает сеть, читает время, проверяет caller cancellation и исходный latch. Проверяются version, обе доступности и token identity. Возраст отсчитывается от начала HTTPS-сбора, а не окончания lookup; каждое новое время сравнивается с предыдущим. Срок проверяется до local work, после открытия, после каждого lookup и после cleanup. Исходные наблюдения не теряются: несогласованные/неудачные ответы остаются в Domain и диагностике, но адрес такой семьи не передаётся GeoIP. При обоих недоступных семействах или отсутствии согласованного адреса база не открывается, положительного решения нет.

Весь интервал включает opening/lookup/disposal. App проверяет consistency database type/build/deadline/hash и привязку lookup к запрошенному адресу/deadline, а успешные страны оценивает существующая Domain policy. Отрицательный lookup, future/stale metadata, ошибка открытия/чтения или invalid adapter result не возвращают Snapshot. Сохраняются collection attempts, database metadata, валидированный отказ lookup и исходное исключение; ошибки lookup + cleanup сохраняются вместе. Caller cancellation имеет приоритет над возвращаемым результатом.

Дополнительный TDD-случай: faulty adapter меняет IPAddress.ScopeId. До исправления сравнение с уже изменённым объектом пропускало adapter mismatch, возвращая Completed с отрицательным Domain.GeoIpAddressMismatch. Теперь строка исходного адреса фиксируется до вызова adapter и результат помечается InvalidGeoIpResult. Это защита привязки, а не утверждение, что adapter независимо подтверждает страну.

Completed означает текущую завершённую оценку данных, а не доступ к сети. Snapshot содержит Evidence, предварительный Decision и живой NetworkSnapshot.Invalidated. Следующий потребитель обязан повторить проверку поколения/сигнала/времени и Domain evaluation: последнее чтение сети не предотвращает будущую смену. Публикация обновлённой базы также не переписывает уже полученный снимок; scheduler/lifecycle должны инициировать новую оценку. Общий выход PowerShell всё ещё не доказан, Permit не открывается, реального Windows monitor пока нет.

9 безопасных интеграционных случаев соединяют настоящий PublicIpReader и MMDB decoder со сценарием/Domain на synthetic fixture и controlled HTTP. Проверены разные страны семейств (US/JP), unknown/registered-only country, unavailable IPv6, missing/corrupt database, источник файла, заменённый между lookup, и invalidation после настоящего lookup. Публичные источники IP, реальные GeoIP-download и mutating Firewall/WFP API не вызываются. Непроверенный live monitor остаётся этапом 7.

## HTTPS-адаптеры публичного IP — 2026-10-24

При `ResponseHeadersRead` таймаут HttpClient заканчивает действие на заголовках. Реализация передаёт один ограниченный CancellationToken через DNS, TCP, TLS и чтение тела; общий дедлайн не заменяется отдельным свежим таймером после заголовков. Размер тела проверяется независимо от Content-Length и ограничен 128 байтами. [HttpCompletionOption](https://learn.microsoft.com/en-us/dotnet/api/system.net.http.httpcompletionoption?view=net-10.0).

Для каждого семейства используется свой Socket и DNS-запрос того же семейства через ConnectCallback. IPv6 DualMode отключён; другой стек после ошибки не подставляется. HTTP/1.1 выбран явно, чтобы соединения проходили через TCP callback. Установлены UseProxy=false, AllowAutoRedirect=false, UseCookies=false, AutomaticDecompression=None, PooledConnectionLifetime=0 и ограничение заголовков 8 KiB. Проверка сертификата и имени остаётся штатной, без callback обхода доверия. Это настройки соединений проверяющего приложения, а не доказательство пути PowerShell. [ConnectCallback](https://learn.microsoft.com/en-us/dotnet/api/system.net.http.socketshttphandler.connectcallback?view=net-10.0), [UseProxy](https://learn.microsoft.com/en-us/dotnet/api/system.net.http.socketshttphandler.useproxy?view=net-10.0), [AllowAutoRedirect](https://learn.microsoft.com/en-us/dotnet/api/system.net.http.socketshttphandler.allowautoredirect?view=net-10.0).

Принят консервативный snapshot диапазонов: исключаются IPv4 special-purpose, multicast и reserved; IPv6 должен входить в опубликованные global-unicast allocations и не попадать в специальные исключения. Отвергаются также globally reachable special-purpose anycast, NAT64, Teredo, 6to4 и неподдержанные новые allocations до пересмотра snapshot. Это проверка допустимого кандидата, не BGP-измерение. Источники snapshot, проверенные 24 октября 2026 года: [IANA IPv4 special-purpose](https://www.iana.org/assignments/iana-ipv4-special-registry/), [IANA IPv6 special-purpose](https://www.iana.org/assignments/iana-ipv6-special-registry/), [IANA IPv6 global unicast](https://www.iana.org/assignments/ipv6-unicast-address-assignments/). Результат не превращается в разрешение при устаревшей базе, неизвестном маршруте или изменившемся поколении сети.

Default endpoints — api.ipify.org/api6.ipify.org и 4.ident.me/6.ident.me, по два настроенных оператора для каждого семейства. ident.me и tnedi.me не считаются независимыми. Используется только plaintext IP, удалённая GeoIP не участвует. Проверены описания API, а не доступность сервисов из приложения на этой машине. [ipify](https://www.ipify.org/), [ident.me](https://www.ident.me/), [документация зеркала](https://api.tnedi.me/). Классификация DNS/TLS/transport ошибок следует типизированному [HttpRequestError](https://learn.microsoft.com/en-us/dotnet/api/system.net.http.httprequesterror?view=net-10.0).

ReadAllAsync сохраняет все попытки и их порядок, не прячет отказ одного источника успешным кворумом. Консенсус остаётся в Domain. Сценарий PublicIpCollector в Application захватывает поколение через тестируемый контракт, отменяет запросы по сигналу смены сети и отбрасывает поздние/неполные результаты. Стандартные snapshots требуют cancellable token; его отмена остаётся видимой после завершения сбора. Реальный Windows-монитор относится к этапу 7. Полная сборка NetworkAssessment должна также включать GeoIP и перепроверку поколения; одних адресных ответов и финального чтения состояния недостаточно для будущего разрешения доступа.

## Мониторинг и отмена проверки

Использовать уведомления о маршрутах, интерфейсах и unicast-адресах IPv4/IPv6, дополнив их периодической проверкой. Публичный адрес после NAT может измениться без изменения локального адреса, поэтому одних уведомлений недостаточно. API уведомлений: [NotifyRouteChange2](https://learn.microsoft.com/en-us/windows/win32/api/netioapi/nf-netioapi-notifyroutechange2), [NotifyIpInterfaceChange](https://learn.microsoft.com/en-us/windows/win32/api/netioapi/nf-netioapi-notifyipinterfacechange), [NotifyUnicastIpAddressChange](https://learn.microsoft.com/en-us/windows/win32/api/netioapi/nf-netioapi-notifyunicastipaddresschange).

Каждая проверка привязана к версии снимка сети. Событие изменения сначала аннулирует разрешение, затем запускает сбор новых данных. Разрешение применяется только для текущей версии. Повторные события можно объединять для перепроверки, но объединение не должно задерживать первичный отзыв. После sleep/resume старые результаты не использовать.

## Идентификация PowerShell и диагностика

Идентифицировать приложение через `FwpmGetAppIdFromFileName0`, а не вручную составленную строку App ID. В перечень входят Windows PowerShell в System32 и SysWOW64 при наличии, PowerShell 7 в Program Files и нестандартные пути из конфигурации. Проверяются установка через Store, portable-копии и обновление путей. [FwpmGetAppIdFromFileName0](https://learn.microsoft.com/en-us/windows/win32/api/fwpmu/nf-fwpmu-fwpmgetappidfromfilename0).

Правило для известного полного пути не является правилом «любой файл с именем pwsh.exe». Неизвестная portable-копия и промежуток между её появлением и обнаружением — отдельное ограничение. Нельзя заявлять полное покрытие произвольных будущих путей. Запрет исполняемых файлов также не запрещает дочерние curl/python/git, встроенный PowerShell в другом хосте или системного администратора.

GUI и CLI различают решение политики, состояние собственных объектов ОС и проверенный сетевой результат. Для неизвестного состояния используется явное сообщение «применение блокировки не подтверждено». Перечисление WFP работает со снимком, созданным при открытии перечислителя, поэтому для последующей проверки нужен новый снимок. [FwpmFilterEnum0](https://learn.microsoft.com/en-us/windows/win32/api/fwpmu/nf-fwpmu-fwpmfilterenum0).

### Реализация прототипа постоянного Block — 2026-10-23

Первый шаг этапа 3 реализован в `src/Windows`. Используются `FwpmEngineOpen0` с учётными данными вызывающего процесса, нединамическая сессия, постоянные provider/sublayer и Block-фильтры для App ID на четырёх ALE-слоях. Наличие provider без service association не рассматривается как доказательство активации после загрузки.

Запись объединена в явную транзакцию; инспекция использует флаг `FWPM_TXN_READ_ONLY`. Ошибки API сохраняют имя операции и полный код WFP/RPC. Контракт транзакций и обработка конфликтов проверены на тестовой сессии, нативные поля и размеры — на x64-структурах, сверенных с установленным SDK. Это не проверка фактической работы BFE с добавленными объектами. [FwpmTransactionBegin0](https://learn.microsoft.com/en-us/windows/win32/api/fwpmu/nf-fwpmu-fwpmtransactionbegin0).

На рабочей Windows выполнен только безопасный интеграционный тест разрешения App ID существующего `powershell.exe`: изменение регистра пути сохраняет идентификатор, результат копируется в управляемую память и освобождается через `FwpmFreeMemory0`. Вызовы создания фильтров не выполнялись. Разрешающий режим продукта, boot-time политика, установка и удаление отсутствуют; Desktop не подключает адаптер. Следующие проверки требуют изолированной VM по матрице, а статус `Present` обозначает лишь совпадение объектов с ожидаемой спецификацией.

### Реализация динамической сессии — 2026-10-23

Для шага 3b повторно сверены `FWPM_SESSION_FLAG_DYNAMIC`, флаги фильтра и арбитраж. Прототип создаёт непостоянный Permit с весом 20 над постоянным Block с весом 10 в том же собственном sublayer; `FWPM_FILTER_FLAG_CLEAR_ACTION_RIGHT` не применяется. Это не обход чужих Block. Условия пока содержат только App ID: такой прототип пригоден для контролируемого исследования механизма, но не доказывает разрешённый общий внешний путь. [FWPM_SESSION0](https://learn.microsoft.com/en-us/windows/win32/api/fwpmtypes/ns-fwpmtypes-fwpm_session0), [Filter Arbitration](https://learn.microsoft.com/en-us/windows/win32/fwp/filter-arbitration).

`WfpPermitLease` проверяет весь baseline перед добавлением первого Permit в одной транзакции и держит динамическую сессию открытой после фиксации. Отзыв закрывает её, не удаляя постоянные Block. Успешный `FwpmEngineClose0` подтверждает закрытие сессии; ошибка WFP/RPC не подтверждает результат. Справка не определяет пригодность handle после ошибки. Поэтому принято консервативное решение: больше не передавать его в нативные вызовы, сохранить ошибку и повторно сообщать её при последующих `Dispose`. Финализатор также не повторяет уже предпринятое закрытие. Это наше решение для неопределённого состояния, а не утверждение, что Windows обязательно инвалидирует handle. В VM потребуется проверить завершение процесса-владельца и фактическую очистку через RPC rundown; ошибка закрытия не считается успешным отзывом. [FwpmEngineClose0](https://learn.microsoft.com/en-us/windows/win32/api/fwpmu/nf-fwpmu-fwpmengineclose0).

Тесты используют fake-сессии и fake close-функции, без реального открытия динамической WFP-сессии и без записи политики. `IsClosed` не означает сетевую блокировку, отсутствие другого владельца Permit или разрыв установленных соединений. Автоматическое удаление при смерти процесса, задержка RPC rundown, зависание, несколько владельцев и срок свежести разрешения остаются непроверенными условиями W04/W05/W09/W12/W23. Подключать этот API как рабочий режим Allow до их закрытия нельзя.

### Прототип удаления политики — 2026-10-23

Удаление выполняется в одной write-транзакции в порядке «фильтры → sublayer → provider». Объект со ссылками из других объектов удалить нельзя; эта ошибка не обходится и вызывает откат. Удаление через динамическую сессию для постоянных объектов не используется. Это следует из ограничений времени жизни и порядка ссылок WFP. [Object Management](https://learn.microsoft.com/en-us/windows/win32/fwp/object-management), [Uninstalling a Provider](https://learn.microsoft.com/en-us/windows/win32/fwp/uninstalling-a-provider).

Для удаления нужен свежий enumerator в той же транзакции. Null template по справке запрашивает все фильтры, но API возвращает только доступные вызывающему для чтения объекты. Поэтому отсутствие объекта в перечислении не считается доказательством отсутствия всех зависимостей. Удаление контейнеров остаётся обязательным и не игнорирует ошибки ссылок или доступа. Страницы обходятся по 128 записей; освобождается массив страницы, а не каждый отдельный указатель. Ошибка обхода, освобождения enumerator или закрытия сессии не скрывает исходную ошибку. [FwpmFilterCreateEnumHandle0](https://learn.microsoft.com/en-us/windows/win32/api/fwpmu/nf-fwpmu-fwpmfiltercreateenumhandle0), [FwpmFilterEnum0](https://learn.microsoft.com/en-us/windows/win32/api/fwpmu/nf-fwpmu-fwpmfilterenum0).

Отбор проверяет собственные provider/sublayer GUID, маркер схемы, постоянство, Block, вес, слой, единственное условие App ID и прежний формат ключа. Совпадение отображаемого имени недостаточно. Для удаления можно распознать собственный disabled-объект, но это не делает его активным фильтром. Permit и неизвестные связанные объекты приводят к отказу. App ID копируется из снимка, поэтому исполняемый файл может уже отсутствовать. После каждого нативного delete проверяется отсутствие объекта по ключу; удаление не является обычным отзывом Permit.

Unit-тесты используют fake-сессии и локально выделенную память. Нативные перечисление, delete, поведение `FWP_E_IN_USE`, readback в write-транзакции и откат в реальном BFE пока не проверены. Эта реализация остаётся прототипом и не заменяет установщик или деинсталлятор продукта.

### Подготовка режима VM — 2026-10-23

Для обычного запуска используется динамический skip xUnit v3 до входа в callback с WFP-операциями. Условия допуска проверяются на подставленных данных; отрицательные проверки действительно проходят как тесты, а не учитываются как skips. Права проверяются по эффективному токену `WindowsPrincipal.IsInRole(Administrator)`, без запроса UAC; ошибка чтения токена не разрешает запуск. [xUnit v3 dynamic skipping](https://xunit.net/docs/getting-started/v3/whats-new), [WindowsPrincipal.IsInRole](https://learn.microsoft.com/en-us/dotnet/api/system.security.principal.windowsprincipal.isinrole?view=net-10.0).

Явные подтверждения оператора связаны с именем машины и существующим снимком. Сам факт аппаратной виртуализации не доказывает изоляцию; скрипт не притворяется, что может проверить сетевую схему и checkpoint из гостя. CI и отсутствие любого условия приводят к отказу до создания правил. Прямой `dotnet test` по умолчанию пропускает единственный mutating test; скрипт VM считает такой skip неуспешным испытанием.

Первый нативный сценарий ограничен объектами для приватной копии PowerShell. Предварительная проверка отвергает даже частичные существующие контейнеры, чтобы тест не принял чужую или старую установку за свою. Снимки полей фильтров читаются в read-only транзакциях и сохраняются в журнал; память страниц остаётся действительной только внутри callback. В случае ошибки выдачи или отзыва дальнейшее удаление baseline не выполняется. Реальные сетевые гарантии, crash/RPC rundown и сроки свежести остаются открытыми: этот сценарий пока не запускался и не измеряет пакеты.
